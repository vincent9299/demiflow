# I08：下一步只针对主路径成本

依据已交付 `POST-STARTUP-BUSINESS-PROFILE` 的 `85733f6` 原 20,000→10,000 / 4 worker 上限 / 256 MiB / 120 秒诊断。它观察到一个业务 worker（PID 19835），fusion 已启用；当前 `fuse_single_worker_pipeline` 和原 `_output→_push` 已能在同一 worker 内执行逻辑链。**重新做“算子融合”、小帧发送或 clone 微调不是当前有证据的主攻方向。** profile 有插桩和并发背景，以下累计时间嵌套，不能相加、也不能转成承诺收益；最终合并版本须重新核占比。

**第一优先：原 cut 的工件/权威往返。** 40 次真实 ACK 对应 358 次 store.put、1,192 次原 artifact request，包含约 3.70 秒 put / 3.37 秒 snapshot / 3.61 秒 request。先按同一 cut 的对象种类、创建与 retain 生命周期分类，找出一次结算中可合并的原 authority 操作；若成立，在原 control-byte/对象数量上限内批量交付同一权威，保持每件 SHA、归属、异常和原 journal/ACK。不能减少 checkpoint、跳过 fsync/验证、造缓存账本，或把延后未完成工作排出计时。准入证明是同输入/原 40 ACK、故障恢复前缀、对象引用/GC、安全拒绝和真实请求数减少；最后才做同文件系统五轮。

**第二优先：融合组内的逐行对象与验证生命周期。** 同一个 worker 中仍有 30,000 次 `_output_record`（累计 3.08 秒）、70,000 次 Record 校验（2.73 秒）和 50,000 次 payload 编码（1.93 秒）。这属于真实中间载荷的生成、冻结、解冻、验证与递归推进，并未被物理同驻留自动消除。值得设计的是原融合组内有界数据载体的生命周期，明确用户可变输入/输出与已验证不可变传输边界，从源头减少重复工作；不是再替换一个 clone 函数。必须保留逐逻辑节点行数/异常定位、tuple/bytes/-0.0、单行/批次上限、用户代码不可变性假设的反例，以及恢复 source_position/sequence。未证明生命周期前不跨 UDF 复用可变对象，不删公共 Record/codec 的验证。

`step` 的约 20.17 秒是包含整个业务的累计值，自身仅约 0.38 秒；不能据此把“批量 step”虚报成二十秒收益。condition wait 的约 5.62 秒包含真实信用与提交等待，也不能一概删除。上述工件和对象成本减少后，再看真实等待是否跟着减少。

**先后与止损。** 在最终候选上用一次原工作负载的业务线程/原 authority 诊断确认这两类成本仍存在，再只选一项有足够占比的改造。普通 map 的无关 Lance 初始化已经移除，Mapping 热路径已交付；原两次 sealed 读取仅约 17 ms，必须保留。终端已验证 wire 复用由另一 lane 处理，同 FS 小样本约 1.52% 且接近噪声，不能替代上述主路径收口。旧 7.92% 是存储混杂观察，不累计为代码收益。真实性门通过后仍保留原九类、五轮与 20% 失败阈值；没有真实可比结果之前，I08 仍未闭环。
