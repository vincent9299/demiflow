# 工作区变化核验与后台巡检：中粒度方案

状态：已获用户批准，A1–A4 已按此设计落地。以下“现状”记录实施前的依据；实际交付、差异和验收见[实施记录](demi-workspace-audit-implementation-20261103.md)。

配套：[源码级方案](demi-workspace-audit-source-plan-20261103.md)、[设计复审与验收矩阵](demi-workspace-audit-review-20261103.md)。延续 C1–C4 的公共能力边界：CLI、HTTP、独立 Web、Harness 插件消费同一套工作区事实。

## 1. 目标与现状

目标：文件被任意编辑器或 coding agent 修改后，能发现变化，核对原检查依据，判断是否超出本次明确允许的文件范围，并在执行入口重新核验。页面关闭不应让执行保护失效；需要持续观察时，可独立运行后台巡检。

当前代码已经具备：

| 能力 | 当前实现 | 当前边界 |
| --- | --- | --- |
| 页面同步 | `web/app.js` 可见时约每 3 秒调用 `workspace_changes` | 元数据提示；页面关闭即停止 |
| 报告依据核验 | `workspace._report_status` 核对源码、声明资源、参数、表引用、平台快照 | 针对指定报告，不是整个项目已验收；读取失败不能等同于已经证明内容被改 |
| 执行准入 | `runs._prepare/_check_basis/_preflight/_resume` 与封存校验 | 已有代码与参数检查；尚未接入通用任务范围约束 |
| 任务修改范围 | DemiForge 的任务基线、writes、readonly 与 check | 属于上层开发规范；平台不能反向读取其私有任务文件 |

另一个实际缺口：`workspace_changes.reports` 主要来自索引修订号。绕过正式写入直接删除、改写报告文件，不一定改变该提示；必须按已绑定的报告摘要直接读取核验。

本轮不做自动修复、自动通过、自动回滚、业务语义判定或模型调用，不新增执行器，不接管生产表的数据完整性扫描。

## 2. 三个判断分开

| 判断 | 依据 | 能说明什么 |
| --- | --- | --- |
| 发现变化 | 路径、类型、大小、mtime/ctime 等轻量标记 | 值得重新核验；不能证明内容一致或改动获准 |
| 检查依据仍有效 | 指定通过报告的内容绑定与现在实际内容比较 | 该报告检查过的对象是否仍对应当前内容 |
| 修改范围合规 | 任务开始时的内容基线 + 明确允许的路径 | 基线之后的新增、删除、替换、修改是否在范围内 |

“范围合规”不等于逻辑正确；“检查通过”不等于业务效果验收。巡检不执行测试、不 import 候选代码，也不把旧报告改写成新通过报告。

## 3. 两个基准、一个工作区绑定

### 3.1 报告基准：明确绑定，不猜测 latest

每个需要持续观察的 `(Flow entry, 参数文件)` 显式绑定一个已通过的报告 digest。保存新报告与将其设为巡检基准是两个动作，可由一次明确的 `inspect --track` 串接。

- 同一 Flow 的不同参数文件分别绑定；不同 Flow 不互相冒用报告。
- 不根据文件 mtime、目录顺序或最近运行猜“上次通过”。
- 运行 prepare 为有效参数生成的内联报告不自动成为开发参数文件的巡检基准。
- 基准替换须核验报告身份、通过状态、入口和参数登记，并现场确认依据有效。
- 未绑定的 Flow 标“未配置巡检基准”，显示已覆盖/未覆盖数量；不显示项目全局通过。
- 历史报告仍可按原 digest 打开核验，不为巡检扫描全部历史报告。

### 3.2 任务基准：固定内容，允许范围独立

开始一次受管修改前，保存所选作者文件范围的真实内容清单，包含当时已有 dirty/untracked 文件。后续比较这份固定清单，不能以 Git HEAD 代替。

基线保存：工作区身份、观察根、文件/目录/不存在状态、文件 SHA256、内容预算和格式版本。允许修改范围以明确的文件或目录前缀声明，不用任意 glob 或业务专属规则。

- 重新检查代码、刷新页面、重启巡检均不移动任务基线。
- 同一任务调整允许范围，保留原内容基线；必须显式操作并携带已观察的控制摘要。
- 增加原先未观察的目录无法补出“任务开始时”的内容，不允许伪装成原基线的一部分。
- 结束任务、开始新任务是明确操作；不因检查通过或 Agent 说“完成”自动清除范围约束。
- 同一工作区同时只有一份生效的范围约束。需要不同隔离范围的并行任务使用独立工作区/worktree，不引入任务仲裁器。

对于 workspace 控制，允许范围可明确包含 `workspace.json`，表示允许其语义字段修改；仍必须通过工作区契约和受影响 Flow 的重新检查。对于生成的结果表引用，只有报告实际使用的引用参与依据核验，不能因正常新增无关结果就判整个开发任务越界。

### 3.3 最小持久结构

现有 workspace v2 为封闭字段契约，不能偷偷增加字段。显式增加 workspace v3；保留 v1/v2 的读取及原有使用方式，不自动升级已有项目。

```text
workspace.json                       # v3 新增 audit 字段
  audit.reports                      # 有限个明确的报告 digest
  audit.change_scope                 # null，或 baseline digest + writes

.forge/audit/baselines/<digest>.json  # 不可变的任务内容基线
.forge/audit/status.json              # 可丢弃的最新观察结果和时间
.forge/audit/watch.lock               # 单工作区巡检租约
```

不新增数据库、任务实体、事件总线或通知服务。报告仍归 inspections，运行仍归原生 journal，结果仍是原来的固定 DatasetRef。

报告选择属于观察配置，不应改变 Flow 的执行语义；现有 `workspace_policy` 不把 `audit` 整体加入每条 Flow 的检查绑定。生效的 `change_scope` 单独绑定到运行准入，改变它会使旧的受管准备结果需要重新准备，单纯切换巡检报告不会。

## 4. 观察范围与指纹

### 4.1 作者文件与运行资产分开

启用范围核验时，必须覆盖 `flows/`、`operators/` 和工作区控制的语义投影；可明确加入 README、测试、Notebook 等作者文件。声明的 config/file 资源目前要求位于 flows/，自然包含在内。

- 文件按完整内容哈希；Notebook 若纳入，包含已保存输出，不只哈希代码格。
- 目录节点、空目录、原本不存在的观察根也记录，发现新增和删除。
- 忽略项仅为契约列出的通用生成目录，如 `__pycache__`，随基线格式固定；不能按文件大小、扩展名或读取失败临时跳过。
- `.forge/`、登记的数据位置、Lance 数据、运行账本和输出不进入作者文件基线。额外观察根与这些运行资产重叠时拒绝，不静默裁剪。
- 表引用是否变化，沿用报告的 table binding 核验；表的版本/schema 可读性由现有接口确认。不会为“工作区指纹”扫描全表或所有图片。
- 平台与环境沿用现有 platform snapshot，不能复制一份新的平台哈希算法。依赖环境当前是 metadata assurance，不能宣称对安装环境做了全字节验证。

本项目整个 `training/` 不纳入本次改造或演示范围；这是项目约束，不写成平台业务特例。旧 pipeline、Notebook 输出和历史产物不改写。

### 4.2 避免控制文件自引用

`workspace.json` 用完整解析后的内容、仅排除顶层 `audit` 字段来计算任务基线中的语义摘要；其他字段均保留。否则写入 baseline digest 本身就会让基线失效。

此投影规则固定在基线格式中，不由调用方自选忽略字段。`audit` 的结构、基线摘要、允许范围及 CAS 由专门校验负责；准备/启动/恢复另行校验其绑定。不用这个投影宣称原文件所有字节都没变。

普通文件的字节变化完整比较。读取使用 no-follow、读取前/打开后/结束后身份与元数据校验、分块哈希和目录稳定性校验。发现读取期间变化，返回“本轮无法完成一致核验”，不发布通过。

## 5. 从变化到执行的完整链路

```text
任意编辑器 / CLI / coding agent 保存文件
                 ↓
轻量标记变化，或周期性完整核验到期
                 ↓
只读核验：固定任务基线 + 受影响的已绑定报告
                 ↓
发布观察结果：依据失效 / 范围越界 / 核验不完整 / 内容仍对应
                 ↓
Web、Harness 插件、CLI 读取同一份状态

prepare / start / resume
                 ↓
独立现场核验当前范围、报告依据、封存内容及既有执行限制
                 ↓
通过才进入对应运行状态；不信任上述观察缓存
```

### 5.1 三个执行入口

| 入口 | 新增约束 | 保留行为 |
| --- | --- | --- |
| prepare | 读取当前生效范围；比较固定基线；封存完成前复核并绑定范围 digest | 继续实际检查此次有效参数；不要求为了形式先手工点击另一个检查按钮 |
| start | 核对准备时范围绑定与当前绑定，再现场核验内容；检查必须覆盖进入 starting 前的最终准入 | 原有 attempt、执行租约、输出 CAS、预算、封存核验 |
| resume | 推进新 attempt 前执行同样检查，随后 start 仍复核 | 原有恢复、预算累计和已提交结果复用规则 |

关键语义：

1. **允许范围内修改**：旧报告可能失效；新的 prepare 可以通过真正的重新检查获得新依据。
2. **允许范围外修改**：即使 Flow 静态检查通过，也不能通过范围准入；须恢复越界内容，或显式修订允许范围，再重新准备。
3. **无关 Flow 变更**：不让另一条 Flow 的报告自动失效；若它违反了当前工作区明确生效的任务范围，则工作区范围准入仍拒绝。这是两个不同原因。
4. **未启用范围约束**：保留既有 Forge 检查，明确显示“未启用任务范围核验”，不冒称修改获准。
5. **运行中修改工作树**：已启动运行使用封存代码，不自动取消、不换代码；后续恢复重新经过准入。取消、读取、核对已提交结果不因范围违规被封死。
6. **检查期间文件持续变化**：本轮拒绝准入或返回未完成核验；不无限重试，也不拿上次绿灯放行。

正式控制更新与准入以现有 control/execution 锁协调。任意外部编辑器不受 advisory lock 强制约束；不能声称整个工作树拥有事务快照。封存执行闭包、稳定读取与最终检查降低竞态并保证执行的已封存内容不被工作树后续修改替换。

## 6. 页面关闭后的巡检

增加一个独立、无 HTTP 依赖的前台长驻命令，由已有服务管理方式托管：

```bash
# 已实现的独立巡检命令
python -m demiflow.cli forge console --registry PATH watch
```

它只负责调度现有隔离 worker 做有限的只读核验。HTTP serve 不再嵌一个巡检线程；不因打开多个浏览器或插件生成多个巡检器。

- 默认约 30 秒观察一次轻量变化；每个被观察对象约 5 分钟到期做一次完整内容核验。
- 完整核验不能因为 mtime/size 相同而省略；平台核验也有自己的完整核验到期时间。
- 这两个间隔是调度目标，**不是所有规模下的完成 SLA**。耗时、排队或不可用使对象 overdue，界面不能继续显示为新鲜。
- 一个巡检进程同时最多一个核验 worker。按工作区和对象轮转，变化合并，不积累无限事件队列；大项目不能永久饿死别的项目。
- 同一工作区持有非阻塞 watch 租约；多个 registry 指向同一项目也不能同时发布状态。
- 启动后即核验；重启不能仅凭旧缓存“继续通过”。失败不移动基线，不能将无法读取的文件视为已删除并判断合法。
- 缓存只保存最新有限结果。CLI、HTTP 手动核验与 watcher 复用核验函数；缓存写入使用短锁/CAS，旧扫描结果不得覆盖较新策略下的结果。
- 退出清理自己的 worker/租约；巡检故障不停止运行，也不取消任何原生任务。

## 7. 状态怎样展示

不增加容易误解的一个全局绿色“安全”灯。至少分开显示：

| 维度 | 状态例子 | 含义 |
| --- | --- | --- |
| 轻量观察 | 最后发现文件变化 10:31 | 尚不代表内容核验完成 |
| 报告依据 | 有效 / 失效 / 无法核验 / 未绑定 | 针对明确的报告与覆盖范围 |
| 修改范围 | 范围内 / 越界 / 无法核验 / 未启用 | 针对固定任务基线 |
| 巡检 | 运行中 / 超期 / 状态不可用 | 不参与执行授权 |

每项携带自己的完成时间、适用的控制摘要和覆盖数量。服务进程还活着，不代表所有报告都刚核验过；轻量轮询也不能推进完整核验时间。

报告失效给出受影响入口、参数、路径和原因；越界给出新增/删除/修改路径。只展示有限明细并明确总数与截断状态，不能因截断丢失失败结论。

Web 继续使用当前单条同步链：`changes` 增加观察状态的轻量修订标记，有变化才读 audit 状态。插件消费相同 HTTP 字段。保留用户草稿、固定运行/表选择；不自动重发写请求，不增加对话入口。

## 8. 公共接口与 DemiForge 的关系

公共模块提供：读取观察状态、只读核验、绑定报告、建立/调整/结束范围。CLI 和 HTTP 只解析协议并调用这些用例，不各自实现判断规则。

第一轮 HTTP 暴露状态 GET 与显式核验 POST；修改基准/允许范围暂用本机 CLI，避免把当前只读/运行令牌直接扩大成修改开发约束的权限。Web、插件照样可以完整展示。执行入口必须从工作区读取生效范围，不能靠客户端是否传了 scope 参数决定检查与否。

DemiForge 已有任务基线，不能让平台直接读取 `.demiforge/tasks`，也不能调用其会保存 check 状态的命令来冒充只读巡检。对接使用中性的基线文件契约：

- 新任务可由上层显式调用公共范围建立接口；平台不创建第二份任务状态机。
- 既有任务的接入须由上层导出**原基线**，验证覆盖、路径、预算、内容算法及控制投影是否兼容。不能用当前文件重拍基线来抹掉已发生的越界。
- 导出无法证明等价时明确拒绝导入，继续原 DemiForge 任务核验；不能宣称完整任务范围已接入。
- DemiForge 私有格式的 exporter 属于上层平台适配。本平台实现不修改 Demiurge；中性导入契约和 fixture 可先验收，真实 exporter 另按该仓规范开发。

## 9. 资源边界

| 增长对象 | 初始预算设计 | 超限行为 |
| --- | --- | --- |
| 绑定报告 | 每工作区最多 64 个；只读取绑定报告，不遍历历史 | 拒绝增加；显示未覆盖对象 |
| 作者清单 | 默认 4,096 项、深度 16；最多 20,000 项、深度 32 | 清单不完整，不返回合规 |
| 文件/总字节 | 默认单文件 32 MiB、总计 128 MiB；可显式提高到 256/512 MiB 硬上限 | 读取前限额，流式累计；不跳过大 Notebook |
| 单次 worker | 继续现有 60 秒 wall time、CPU/内存/输出限制 | 超时为无法核验；清理子进程 |
| 核验输出 | 最多 1 MiB，细节最多 256 条；完整清单另有 8 MiB 上限 | 保留失败/不完整状态及总数，拒绝超大控制 |
| 基线存储 | 每工作区最多 1,024 份，合计 256 MiB；写前留足临时空间 | 拒绝新建，显式处理保留策略；不自动删历史 |
| watcher | 单 worker；registry 沿用最多 128 项；对象调度集合有界 | 延后并标 overdue，不增加并发补欠账 |

较大预算只是允许尝试，不保证 60 秒内完成。若实际规模持续超时，明确报告容量不足；不通过无限 timeout 或增加并行扫描掩盖问题。多个 HTTP 请求与后台 worker 的并发相加计入验收；单工作区额外审计操作租约避免多端同时扫描同一基线。

以上不自动提高 source discovery、现有 workspace 列表、报告或运行的其他限制；同一操作同时受到多个限制时均须满足。完整稳定性复核所需的重复读取计入任务时间和 I/O，不把“清单内容 128 MiB”写成整轮只读取 128 MiB 的保证。

## 10. 不承诺的保证

- 周期扫描不能保证捕获两个观察点之间“修改后又完全恢复”的瞬时变动。
- 指纹不判断作者意图，不证明业务正确，不证明代码没有漏洞。
- 与服务同权限的系统用户可以修改程序和控制文件；这不是恶意代码沙箱或安全权限系统。正式 API 无法省略范围参数绕过检查，与恶意操作者直接改平台是两个边界。
- 本轮不扫描数据行、图片字节、全部历史报告/运行，不能称为全仓防篡改。
- 原始 Dataset 或旧脚本直接执行不经过 Forge 准入。旧 pipeline 保留使用；必须明确它们是否进入受管执行，不能把 Forge 的保证扩大到所有 Python 进程。
