# 单卡性能复核：并行、CUDA Graph 与流水重叠

本文保留当时的原型记录。pplx 后续正式集成的任意形状缓存、资源上限和服务
验收见 [2026-11-01 集成复核](pplx-cuda-graphs-review-20261101.md)。

本轮区分三件事：两卡副本是横向扩容；同卡不同 CUDA stream 的内核重叠才是
单卡执行并行；CPU/HTTP 与 GPU 重叠是流水优化。三者不能混称。
只使用用户授权的 GPU 0/1，未使用 GPU 2/3，未修改已安装模型环境或权重。
证据目录：`/tmp/demiflow-single-gpu`。

## 1. pplx 单卡并行确实发生，但不能盲目加线程

在 GPU 0 上只加载一份完整权重。多个执行实例共享不可变参数，分别持有模型
模块状态、临时张量和 CUDA stream；原生 encoder 的调用互斥。每次推理仍走
原生单请求 `decide`，没有拼接请求、改变 batch 形状、量化或更换计算内核。
每个请求完整同步并读取结果后才计为完成。

| 模式 | 吞吐（条/秒） | p50（ms） | p95（ms） |
|---|---:|---:|---:|
| 1 stream，8 CPU 线程 | 10.38 | 92.57 | 140.35 |
| 2 streams，8 CPU 线程，首轮 | 9.90 | 204.04 | 232.28 |
| 4 streams，8 CPU 线程 | 8.71 | 449.67 | 552.12 |
| 1 stream，1 CPU 线程 | 10.50 | 92.55 | 139.91 |
| 2 streams，1 CPU 线程 | 11.25 | 174.02 | 212.12 |
| 2 streams，8 CPU 线程，后续三轮 | 11.39 | 173.15 | 192.49 |

最后一行是 200 个不同输入随机混合三轮共 600 次。所有模式与此前直接调用
原生模型的单条基线比较，标签变化 0、概率差 0（固定容差 `1e-6`）。
首轮与后续有波动，不能宣称增加线程稳定获得固定倍数；尾延迟确实上升。
Torch allocator 采样峰值：单流 reserved 50,672 MiB，四流 51,752 MiB，
后续双流 51,864 MiB；这是 allocator 数据，不冒充整个进程显存。

短片段 profiler 记录了两次独立请求的 9,090 个 GPU kernel，来自两个 stream。
总 kernel 忙碌时间约 73.61 ms，其中约 27.22 ms（36.97%）有跨 stream kernel
重叠，峰值同时两个 stream。这是单卡真并行证据，不只是 HTTP 或 CPU 线程同时存在。
该比例仅描述这个短片段，不推广为整个任务的平均利用率。
证据：`pplx/report.json`、`pplx/two-streams-trace.json`、`pplx/trace-summary.json`。

## 2. 不改变输入形状的 CUDA Graph 原型

为减少 Python/CPU 发射 kernel 的开销，实验捕获原生单条计算图；保持 BF16、
原生层、原生 readout 和校准。只针对精确 `(token 数, 问题数)`，不通过补 padding
凑形状，不把多行合为一行。每个 stream 最多准备 8 个图，其他形状走原生 eager。
每个图保留全部输入/索引/mask 张量并持有独立内存池，避免异步存储被回收或复用。

| 同一组输入 | 原生单流 | Graph 单流 | Graph 双流 |
|---|---:|---:|---:|
| 全部 200 条混合输入 | 10.45 条/秒 | 12.50 条/秒 | 15.00 条/秒 |
| 其中命中图的 58 条短输入 | 11.36 条/秒 | 27.93 条/秒 | 33.30 条/秒 |

全量双流运行三轮 600 次，174 次命中图，426 次走原生 eager；标签变化和最大
概率差均为 0。相对于这一轮单流全量基线约 1.44×，不是把短输入子集的
2.93× 当作全量提升。图命中子集也按同一子集的 eager 对照。
双流混合 p50/p95 为 166.00 / 199.16 ms；这比单条基线更高，吞吐与单请求
延迟仍有取舍。整轮 allocator reserved 为 51,536 MiB。

**这仍是原型，未加入平台默认或公开服务配置。** 8 个形状来自已知样本的高频
形状，测试不包含动态图准入、缓存淘汰、冷启动摊销或真实业务的未知命中率。
实际走图的不同输入只有 58 条，200 条全量通过不能冒充 200 条都验证了图路径。
首次原型还暴露静态索引/mask 生命周期问题；已在隔离进程中修正并重跑，
没有让失败原型进入服务。正式集成需要独立的资源预算、输入覆盖和生命周期验收，
不能将“本次测试零差异”自动扩张成所有形状/图片的证明。
证据：`pplx-graphs/report.json`、`pplx-graphs-r2.log`、`pplx_graphs.py`。

## 3. JEV：已接入正式服务的单序列流水优化

现有 vLLM 同引擎跨请求计算会进入 continuous batching，前轮质量未通过。
本轮保持引擎 `max_num_seqs=1`，仅让 CPU 输入准备、HTTP 往返和下一请求排队
与当前 GPU 请求重叠。GPU forward 仍最多一个，不将它宣传为单卡多 forward 并行。

原生后端测试：单条 12.60 条/秒，两个在途请求 13.64，四个 13.55，八个 13.79。
2/4 并发各跑三轮 600 次；所有模式标签和概率差均为 0。八个在途请求 p95 达
1.10 秒，没有与尾延迟相称的额外吞吐收益，因此不建议盲目堆积排队。

正式实现只扩展现有 profile 与 wrapper：当且仅当托管 JEV 配置显式声明
`options.max_num_seqs: 1` 时允许请求准备重叠；能力仍报告 `parallel: 1`、
`continuous_batching: false`、`batch.supported: false`，另报告
`request_pipelining: true`。静态配置、batch 验收入口和 worker 均拒绝将此模式
与 batch 证据混用。其余默认路径的执行锁和质量门槛保持原语义。
行调度、预算、journal、重试、启停仍复用原实现，没有新增执行器或线程池。

配置方法见 [使用说明](model-services.md)。原生证据：`jev/report.json`；
真实服务对照、1k smoke 与停机重放证据：`jev-service-final/report.json`。

正式 wrapper 交替运行三轮单在途、三轮双在途，每轮 200 条，消除只拿早期基线
与后期热态结果比较的问题。600 条单在途汇总吞吐 12.77 条/秒，600 条双在途
14.04 条/秒（约 +9.96%）。三轮 p95 的中位数分别 196.85 / 305.53 ms。
所有结果与原生单条基线的标签、概率差均为 0。另跑 1,000 行真实算子 runtime
调用，64.79 秒、1,000 请求/响应、0 HTTP/transport 错误；停掉模型并禁止 bind
后重放全部 1,000 行，0.49 秒、结果一致、无新增请求或模型启动。
这项小幅吞吐优化已接入公开配置；未将上述实验性 pplx 图执行器混入平台服务。

## 4. 如何理解“GPU 100%”

`nvidia-smi` 的 GPU utilization 是采样窗口内至少有一个 kernel 执行的时间占比，
不是 SM、Tensor Core 或 HBM 带宽利用率达到理论峰值。`utilization.memory`
同样是显存读写忙碌时间，不能当作已用带宽除以峰值带宽。
定义见 [NVIDIA nvidia-smi 文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

首轮 GPU 0 利用率采样窗口中有外部 d3 服务启动，因此
`pplx-utilization/` 的整卡利用率不作为独占 GPU 验收证据。保留原始数据说明
干扰来源，不停止或修改外部服务。改在空闲 GPU 1 上运行独立复测，每次轮询
同时核对 NVML 的 compute PID 集合必须只含本次测试进程。
复测使用 NVML 每 0.2 秒轮询，只统计每阶段去掉首 1 秒、末 0.5 秒后的窗口。
NVML 自身采样周期可能更长，轮询点不视为独立统计样本。
最终证据存放于 `pplx-utilization-isolated/`。

| GPU 1 独占复测 | 请求数 | 吞吐 | 利用率均值 | 中位数 | 最大值 |
|---|---:|---:|---:|---:|---:|
| 全量混合，原生单流 | 200 | 10.75 条/秒 | 55.41% | 52% | 100% |
| 全量混合，Graph 双流 | 600 | 15.76 条/秒 | 66.99% | 60% | 100% |
| 58 条图命中短输入重复 12 轮 | 696 | 33.69 条/秒 | 99.45% | 100% | 100% |

每个轮询点的进程集合均只含本次测试 PID。最后一行运行 20.66 秒，稳态窗口
96 个轮询点全部至少 95%，75% 的点为 100%，范围为 95%–100%。三种模式
整卡显存采样峰值约 52,499 / 53,107 / 53,107 MiB。全部标签和概率差为 0。
这是单卡短输入在图全部命中、持续供给条件下接近满忙的有限时长证据，不能
承诺任意输入持续 100%。混合输入只有 29% 命中图，吞吐提升约 46.6%，
并非短输入子集的 33.69 条/秒。前次未受干扰的全量复测为约 43.6%，应保留波动。
前轮受干扰的 GPU 0 利用率结果已剔除，不混入此表。

短输入、CPU 发射间隙、请求到达不连续都影响忙碌比例；增加排队或重复无用计算
可以使显示值更高，却不等于有效吞吐更高。验收顺序是输出一致性、有效吞吐、
p95 延迟和显存边界，然后用 profiler/利用率解释瓶颈；不把持续 100% 作为承诺。

CUDA stream 的依赖同步与图张量生命周期遵循
[PyTorch CUDA semantics](https://docs.pytorch.org/docs/2.14/notes/cuda.html)。
原生 vLLM 的 batch-invariant 功能有模型/后端范围，不能由文档中存在该开关推导
当前 JEV 的 GDN 后端受支持；参见
[vLLM Batch Invariance](https://docs.vllm.ai/en/latest/features/batch_invariance/)
及前轮实测失败记录。
