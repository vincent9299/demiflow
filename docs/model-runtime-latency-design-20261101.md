# 原生数值稳定性与单卡尾延迟设计复核（2026-11-01）

保持原有 services、模型适配、算子/journal 边界，不改已有服务或模型安装环境。
只使用授权且空闲的 GPU 0/1，保存所有失败试验和本轮开始的工作树基线。

## JEV：先定位实现，再决定修复与并行

1. 多次独立启动相同原生 vLLM/JEV 配方，保存原始 logprob、答案、usage、运行时
   配置；同时比较之前两组不同基线，分清进程内、跨启动与跨调度形状的差异。
2. 在临时诊断进程内，对原生 GDN custom-op 与双向 attention fix-up 的输入/
   输出逐层取完整 tensor 指纹；先确认探针不改变答案，再定位第一个分歧阶段。
   之后只对该阶段做控制变量回放，不能把某个下游差异冒充最早起点。
3. 单卡真正并行必须隔离可变执行状态、缓存和 stream，权重可以共享。不能把
   vLLM 的内部合批或两个 GPU 副本计作单卡独立 forward 并行；不能因为 HTTP
   并发通过就解除质量保护。若当前原生实现不支持安全隔离，应记录具体限制。
4. 修复只在根因与原生输出对照证据支持时集成；不调宽容差、不更换基线掩盖失败，
   不直接修改已安装的 vLLM、插件或权重。

## Torch 三后端：减少捕获和排队开销

优先核对同步捕获中的重复 warmup，及多个新形状同时要求独占 GPU 时的阻塞。
图捕获仍需相同静态输入布局的一次原生预热，覆盖编译/模块初始化；原生对照和
首次/周期精确校验保持。再评估有限的捕获节奏，避免短时间内连续捕获影响正在
服务的请求。不增加后台 GPU worker、无界预热任务或第二套请求调度。

公共执行层统一实施，pplx/AMOS/d3 不分别维护三个策略。捕获、校验、淘汰仍需
正确管理 GPU 地址生命周期和 cuBLAS 工作区，不能为减小 p95 移除必需的同步。
排队优化须检查公平性与取消/关闭；所有准入、缓存、工作区和捕获预算保留。

## 验收与选择

先 CPU 契约/边界测试，再原生基线 + 相同 200 条业务分布的冷、混合和有排队
负载，比较吞吐、p50/p95/p99、捕获次数/耗时、显存；概率与 usage 精确一致。
既测优化前后，也测最终热缓存，不能用捕获更少或请求更少单独宣称性能提升。
加入不同长度、缓存淘汰、质量故障和资源不足回归。若一种策略仅把尾延迟转移
到另一个阶段或显著牺牲吞吐，须明确取舍而非隐去数据。

## 实验后的架构复核

本轮实际采用 FIFO 准入和减少重复静态预热，没有新增捕获调度器；等待者仍由
服务 `max_inflight` 限制。FIFO 在工作区不足时可能使后面的较小请求等待，具体
取舍和完整 GPU 数据见 [验收复核](model-runtime-latency-review-20261101.md)。

JEV 找到的 FlashInfer scratch 共享缺陷属于后端实现，候选补丁独立保留，不在
公共 services 层全局 monkeypatch。单卡并行实验必须先隔离 GDN/KV/输入/Plan，
再以固定 lane 的 CUDA Graph 重放；捕获仍需独占，不能并发切换 vLLM 的全局
ForwardContext。正式集成还须以固定版本的后端接口拥有这些状态，复用平台既有
预算、缓存、质量门槛及生命周期。临时诊断脚本中的私有对象复制不会直接进入
公共运行时，跨启动的旧数值差异没有被重新定义为“通过”。
