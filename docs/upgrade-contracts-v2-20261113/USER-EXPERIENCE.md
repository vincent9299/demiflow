# 两大意图完成后，用户实际看到什么

这是完成后的验收目标，不是当前已完成声明。对应实现见 FUNCTION-TASKS.md，证据门见 INTEGRATION-ACCEPTANCE.md。既有公开 API 尽量保留；内部的新类不要求业务用户学习。

## 一、产品：一个能完成工作的工作台

### 1. 打开项目就能继续工作

左侧选择业务项目，右侧保留开发、管道、数据、Readme 四个 tab。侧栏收起后内容区自然扩展，图、表和编辑器随窗口变化；主要按钮不藏到不可达区域。切 tab 不丢已保存配置、Notebook 输出、Case 草稿或开发对话。

开发 tab 保留该项目的会话及历史，Readme 展示项目说明。项目选择、授权来源和工作区路径一致；仅仅看到一个项目，不代表有权执行它。

可验收的动作：打开旧项目→展开旧开发记录→切到管道→收起侧栏→改变窗口宽度→返回旧记录。历史内容和当前选择仍在，错误有具体原因。

### 2. 管道页先回答“这份代码会做什么”

选择入口和参数后，图展示实际代码的输入、转换、分支、共享祖先和输出。点一个节点可以看到对应源码、参数、输入输出字段及检查问题。相同函数出现两次时是两个执行位置，不能合成一个节点后混用状态。

运行前的图明确叫“声明图”；选择历史运行后展示“运行封存计划”。二者可以切换查看，但来源不能混淆。没有封存计划、载体损坏、节点映射不完整时，显示具体不可用原因；不能补算一张图后冒充历史事实。

图的来源和运行状态分开：封存计划说明运行固定了什么；运行中、失败、已取消、已提交以及行数等来自真实运行记录。存在 dag_id 不代表执行成功，统计页中没出现一个节点也不等于该节点从未执行。

可验收的动作：同一函数在两个分支使用不同参数→检查两节点→运行→选择某个 attempt→分别看到各自源码/参数/状态；更改当前代码后，旧运行依然展示原封存内容。

### 3. 配置、检查、启动是一条连续路径

用户改参数和目标，点击检查；系统能定位具体节点/字段错误。修改入口或参数后，旧检查结果会显示过期，不能拿旧摘要启动新配置。

检查通过并启动后，运行绑定当时的代码、参数、固定输入、输出意图和资源限制。用户无需手写 execution_bindings、program_id 或 checkpoint。失败也必须产生准确结果：配置无效时不先读数据、建模型客户端或写目标；预算不足告诉用户哪个声明无法准入。

可验收的动作：先故意填错字段→点击检查→定位并改正→重新检查→启动→看到实际运行和输出。检查的那份配置必须是执行的那份。

### 4. 运行页能解释进展，也能正确停止和恢复

每次运行有 run，每次尝试有 attempt。用户能切换 attempt 查看图、参数、节点观测、日志、实际输出和失败原因；历史输出标明来自哪个 attempt。

点击停止后，页面显示停止正在进行，待真实执行单元退出才显示已停止。迟到线程、仍在发出的模型请求或待确认提交，不会因为按钮变色而消失。

支持恢复的运行，从已提交边界继续，保留 Actor 状态、分组/批次余量、路由序号和已保存模型响应。已经确认的输出不重复提交。代码变化、目标被外部创建、请求结果不确定等情况会明确拒绝恢复；不会自动覆盖目标或重发可能已经收费的调用。

特别场景：write_table/create 在目标尚未发布时中断，只有原 action、目标、operation_id、请求摘要全部一致且目标仍不存在，才准入恢复。append/overwrite/merge 不套用此特例。

可验收的动作：跑真实流程→中途停止/模拟进程退出→恢复→比较最终结果与不停机执行。行数、内容、浮点符号、重复项语义、模型新请求数及最终目标提交次数都要符合契约。

### 5. 数据页可以直接分析真实结果

用户能浏览注册数据、表字段、固定版本、样例、统计和分布。运行结果进入目录时来自真实提交 receipt，不能靠“文件看起来存在”登记为成功。

同一 Notebook 支持 Python 和 SQL，保留代码、输出、命名结果和结果间引用。保存后重开能继续工作；取消与重启作用于该 Notebook/kernel，旧 generation 的迟到输出不能覆盖新结果。它不被强制包装成一个 Pipeline run。

输出按类型渲染：表格、message/dialogue、text、Markdown、code、JSON、图片、音频、视频、tag、HTML。长表和媒体有分页/读取上限，不一次加载全量数据；缺文件、过期引用、权限问题显示真实错误。

可验收的动作：从已提交管道结果打开表→SQL 选样→Python 处理→把结果固定并重新打开→取消另一条长查询→原固定结果仍可读。

### 6. 比较和评测可以靠配置完成

Case 页可以按业务分组、筛选、选样、翻页；“已标注/未标注”等条件由服务端真实标注状态过滤，不能只在当前页藏行。

同一个 Case 同时展示共享输入/参考、多方案及多字段。字段角色、媒体预览和对比/画廊布局由配置控制。更换评测字段或方案无需重新写查看器。

Case 级、方案级、字段级评分分别保存；“保存并下一条”不会丢草稿。重新打开能恢复草稿、查看历史；另一个页面更新过同条评测时发生明确版本冲突，不静默覆盖。

可验收的动作：配置两个方案、三个字段→按未标注筛选→评测一个字段和整条 Case→保存下一条→重开并验证范围隔离→两个窗口制造一次冲突并正确处理。

## 二、数据流引擎 API：业务写法统一，执行语义可靠

### 1. 写业务算子，不手工拼执行系统

公开入口仍是 Dataset。下面使用当前已有的方法名和参数；完成目标是这些合法组合保持可用，并通过相应验收。

```python
from demiflow import data

rows = (
    data.from_items([{"x": 1}, {"x": 2}, {"x": 3}])
    .map(lambda row: {"x": row["x"], "double": row["x"] * 2},
         execution="thread", concurrency=2, queue_depth=4)
    .take(2)
)
# 期望：[{"x": 1, "double": 2}, {"x": 2, "double": 4}]
```

合法 thread map 的 take、iter、count、materialize 和写表不能因为共用预检而整体退化成“不支持”。take(0) 返回空列表且不读源、不构造 Actor；无效选项仍在副作用前拒绝。take/iter 是向调用者交付数据，不能因此承诺“调用者上次收到的行可以自动跨进程恰好交付一次”。

### 2. 普通有状态算子能走明确的恢复协议

```python
class Counter:
    def __init__(self):
        self.n = 0

    def __call__(self, row):
        self.n += 1
        return {**row, "sequence": self.n}

pipeline = data.from_items([{"x": 1}, {"x": 2}]).map(
    Counter, execution="thread", concurrency=1
)
```

目标行为：这种只有普通 JSON 字段的实例由平台保存语义状态。类工厂在编译时不实例化；运行时构造后、首行前重新检查并登记，恢复时 n 不归零。并发为 1 是此例为了定义全局序号，不能把所有并发算子的设置偷偷降成 1。

复杂资源型 Actor 仍用原生适配器或明确的 snapshot_state/restore_state/recovery_identity。锁、连接、线程和任意外部 Python 对象，不会被自动序列化成“可靠状态”。函数闭包中的可变外部副作用也不因接口简单而自动获得恢复保证。

### 3. 落盘与恢复仍然使用原运行上下文

```python
from demiflow.execution import RunContext

with RunContext("/tmp/demiflow-example/run", entry_identity="example-v1"):
    receipt = pipeline.write_lance(
        "/tmp/demiflow-example/result.lance",
        mode="create",
        return_receipt=True,
    )
```

RunContext 目录、原入口、输入和输出意图是恢复依据。受支持的中断恢复使用同一目录及 `resume=True`；工作台通过自己的 resume 入口完成这些核验。恢复不会重新生成 pickle 后把新摘要当成历史依据。不要把示例当成可重复执行的覆盖脚本：create 目标已存在时按原契约拒绝。

结果提交仍由 driver 唯一负责。worker 提供执行贡献，不能各自提交；排队的 ACK 有有限等待和取消，超时不会变成“没有发生”。

### 4. 流式、关系运算和原生后端能组合，但边界明确

```python
left = data.from_items([{"id": 1, "a": "A"}])
right = data.from_items([{"id": 1, "b": "B"}])
joined = left.join(right, on="id")
result = joined.take(1)
```

join/union 的每个真实子计划都进入执行图、代码固定和布局绑定。改右侧 UDF 不能漏过恢复检查。原生后端接收同一份封存预算和后端选择，不能执行时换一套配置。

需要把流式过程作为关系输入时，使用已完成的显式 materialize 边界；不支持的惰性组合在执行前说明原因，不隐藏一个无限物化过程。空输入、重复键、多重性、缺失/空值和顺序承诺都按原 API 保持。

### 5. 模型与向量能力是原生组成部分

Embedding 仍调用现有 `map_embeddings(model=..., inputs=..., output=..., batch_size=..., concurrency=..., request_policy=...)`；Prompt 仍使用现有原生 Prompt 配置。用户配置模型、输入、输出和请求策略，不另外维护恢复数据库。

已保存响应在恢复时重用；fresh 配额只计真实新请求。批次大小和并发来自声明，不能为了通过恢复测试强制改成 1。发送过但结果不确定的请求默认停止并报告，不能自动补发。向量搜索固定表版本，恢复不会追随新 HEAD。

### 6. 资源限制会影响真实执行

同一 run 的 reader、队列、Actor、批次、状态、输出及原生后端使用同一资源体系。预算不足在适当阶段明确失败；单个超大行不能绕过字节限制；慢消费者会产生背压，不无限缓存。

行保真包括 list/tuple/bytes 区别、bool/int/float 区别及 -0.0 的符号。结果比对按承诺的顺序/多重性，不能为了让摘要一致而改业务值。

历史 read API 不执行当前业务代码。链式、graph、queue、本地原生及实际声明的 Ray 路径，各自有真实验证；本机测试不能冒充多机、GPU 或全部后端已验。

## 什么才算两部分同时交付

以“真实数据→配置检查→引擎执行→提交结果→工作台查看→Notebook/Case 使用”为主线，再逐个覆盖失败、取消、恢复、历史与预算反例。每条链路必须用实际实现串起来。函数单测全部绿色、静态契约检查通过、或 UI 图看起来正常，都不能单独等于这份目标已完成。
