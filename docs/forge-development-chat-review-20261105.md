## 2. 本地执行部署取舍

支持两种**显式配置**的部署模式：

- `restricted`：只有真实文件、网络及子进程探针通过后才开放相应能力；本机 bwrap 失败必须如实显示不可用，不能自动降级。
- `trusted_local`：允许作为单操作者可信本机环境的实现和验收路径，使用宿主已有 OS 权限；不修改宿主安全配置、不安装宿主服务、不自动切换到此模式。项目范围、应用层许可、预算、检查和进程清理仍必须落实。能力页明确没有 OS 文件/进程隔离，不得声称可以防止同 UID 进程读写其他位置、工具联网或改动控制文件。

这是产品架构选择，不是通过提示词制造沙箱的承诺。首版不为隔离单独建设远程 runner 平台，也不因当前容器缺少 namespace 能力无限等待。默认不开启新开发能力，服务部署必须明确选择模式与项目；不能从既有 `allow_runs` 推导开发许可。正式服务启用仍在最终具体交付 Review 时核对，不在本次设计审阅中直接变更服务。

受限模式的强制保障和可信本地模式的应用策略应在能力与验收矩阵中分开。相同 UID 下的本地文件和 HTTP token 不是抗恶意代理的审查身份系统；两种模式都不得把模型自述、伪造 stdout 或自身审查当独立验收。不要给普通已授权开发额外增加反复确认流程。

## 3. 规范执行与记录一致性

接受复用适用 AGENTS、任务实际绑定的标准/Skill、公开开发 CLI 和当前真人要求。薄工具桥仅装配现有协议，不能复制检查规则，也不能改旧基线来消除越界事实。已有授权范围明确时直接登记并执行必要步骤；复杂任务的设计 Review 仅按实际要求适用，不扩成每个 turn 都待批准。

实施需明确 `context --read` 与 provider 送达之间的失败窗口。旧 CLI 的读取回执不能自动证明新 turn 已得到正文。记录准备、发送及已确认/不确定状态；provider 发送失败或结果未知时不把页面标为本轮已送达，不启动依赖未送达规范的编辑。续聊补送相同摘要内容，不伪造回执、删除旧记录或自动重新执行未知副作用。

源文件、任务基线、先前 dirty 内容、Notebook 输出、当前检查 revision 分别保留。上下文冲突或必读内容超限须明确处理，不能悄悄删规范或缩小 watch。未注册项目可讨论和暴露接入缺口，不能显示已经获得受管验收。

## 4. 模块与资源边界

接受小型 `development_chat` 模块及能力适配器，不导入 `development.tasks` 内部 API。复用现有 Markdown、认证、项目解析与原生进程身份机制。低层 transport 只抽取已有真实共用部分；不要为了两种客户端统一而大改稳定的行算子或扩大公共接口。若必须修改旧算子传输，保留其原有语义并做对应回归。

资源核算必须包括：控制数据库及 WAL/rollback、provider 私有目录、临时文件、输出分段、未清理后代、事件多份副本和浏览器订阅。会话/turn/事件数量也要有界，不能仅给单帧限额。新执行单元的身份与预留须在启动前持久化；发送/启动结果未知保留归属，cleanup 未完成不释放相应资源。

开发与作业运行管理共享宿主时，分别的“全局”额度不能冒充宿主合计上界。实施给出两者同时运行的总预算、磁盘设备账目和余量；优先复用低层记账或显式划分固定子预算，不再引入调度系统。SSE/长轮询必须受现有 HTTP 总容量约束，慢订阅不囤积输出；停止请求可达性的声明以实际连接满载测试为准。

采样 RSS/后代计数、单进程 RLIMIT 和原子字节准入分别说明保证。未知 provider 内部请求/费用不可标为封顶；应用不自动重发付费 turn 或切供应商。
