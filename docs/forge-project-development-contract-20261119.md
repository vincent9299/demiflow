## 已确认的问题

- candidate.10/v3 已支持同一项目拥有多条流程。原开发授权的源码目录也能新增文件，但开发桥缺少受控声明登记；CLI 不能写两个控制文件，原绑定又将所有声明变化视为权限漂移。
- 新请求被加入原会话，但上下文突出第一条目标，缺少“当前项目需求”的明确语义。首个示例目标不能成为项目永久的功能白名单；原始要求、后续真人要求和现有行为均保留。
- 代理能登记待澄清问题，受管桥却不能用后续真人回答解除问题。未答问题只在最终接受时阻断，造成无效的验证与独立 Review。
- 原试用项目是两个流程的受限合成示例。其通过记录证明既定范围内的修改闭环，不证明任意新流程都已打通。

## Owner 与边界

- CLI 继续拥有模型/工具循环，在已有授权目录新增或修改代码、测试和参数。独立算子复用已登记算子目录与当前 AST 目录发现，不另建算子登记体系。
- Forge 拥有版本化规范、项目开发声明、原始基线、精确声明修订及当前验收证据；不依赖工作台实现。
- 工作台拥有 workspace 的流程/参数登记与会话生命周期，复用现有 `register_flow` 的静态验证和控制文件 CAS，单向调用 Forge。
- B1 执行边界、固定 verifier、数据与运行权限不变。新流程代码不能任意修改规范、平台、控制文件或生产数据。

本轮实现位于 `gpt_project_development_20261119` / `fix/project-development-20261119`，从指定候选 `75ab567` 建立。候选 `gpt_prompt_replay_20261118` 当前为运行来源，修复验证后才合回并切换；主仓不做产品开发。

## 澄清闭环

1. `note(question)` 保留原问题和可信来源。投影明确表示需要补充信息，存在未答问题时不运行固定验证或独立 Review，也不自动续修。
2. 用户继续正常发送消息。控制器先把原文作为带稳定 event ID 的真实 decision 保存，再交给 CLI 理解。
3. 桥新增 `resolve_question`，模型只提供 `note_index`。控制器优先引用当前 turn 已送达的原生 `requestUserInput` 真人回答，否则导出当前真实消息的完整分段 decision IDs；审批回复及模型文本不能作为答案。领域只允许引用在该问题之后的真实 decision，禁止自造答案、旧消息或同轮自问自解。
4. 解答记录引用原始问题与完整真人回答，独立 Review 能检查其业务含义。解除问题不改变权限；回答不足时可继续提问。
5. 同一解答幂等，冲突解答拒绝。原 goal、基线、历史收据及会话身份保持。

## 新流程登记

CLI 只可提出 `register_flow(flow_id, path, symbol, params)`。owner、请求身份、turn/epoch、真实用户依据及预期版本由控制器绑定，不能由模型指定。

- 仅新增已有项目 owner 内、已有 writes/watch 内的独立公开 Python 入口。参数文件同样位于已有写范围，不能在 readonly 范围；复用现有 AST/JSON 验证，不导入执行候选代码。
- 不覆盖、删除已有流程或给旧入口改配另一份参数；不改变 standard、工具来源、sources、watch、readonly、verifier、数据位置或运行权限。
- 每个原始 turn 至多 8 项登记意图，项目仍遵守 64 个 named flow 上限。重复请求保持幂等。
- 桥只持久化有类型的意图。开发进程排空后，由现有门禁生命周期执行登记；不让控制桥线程在清理后继续修改项目。
- workspace 与 Forge 声明的修改共用项目控制锁。在 Store 写事务内最后复核 active/epoch/stop/primary/policy/root，然后记录 durable pending、执行双 CAS、提交精确声明修订。
- 原 binding、baseline、readonly_baseline 保留。新增受信修订记录两份声明的精确 before/after，当前指纹、检查和 Review 消费完整修订链；不能把一般外部改写认成受控登记。
- pending 阻断当前验收。中断前两份均未写且已取消时可中止；半写仅按已记录的精确 after 恢复一致性，不复活执行或签发接受；任何陌生字节都保持阻断。
- 应用后在同一原 turn 的有限预算内续行，重新装配、送达上下文并执行门禁。注册成功本身不代表开发验收或运行授权。

## 验收与升级

验收必须覆盖同一项目/同一会话新增流程、共享或独立算子、问题回答后继续、工作台目录可见与计划预览，以及越界、重复、取消、双 CAS 中断和历史保护。测试不得只对已有函数再改一个常量。

平台实现升级需主协调单独核对精确前后版本、服务排空和原记录备份。不得遇到旧绑定 stale 就自动重建任务/基线，或让用户用“新任务”掩盖连续性缺陷。旧证据保留为原版本历史，当前版本重新验证。

真实新流程验收两次遇到独立审阅的 16,384 token 截断，简洁提示单独不能消除。该审阅请求上限调整为 32,768 tokens，stream 事件最多 65,536；保持 low、180 秒、每原始 turn 最多两次审阅、64 KiB 最终 JSON 与 256 KiB 流字节限制。七项完整结论、证据校验与失败关闭保持；不拼接截断输出、不以自评替代，也不自动重写或重放原来失败的 turn。开发 CLI 的单次模型额度不变。

根目录 workspace 复用公开 v3 声明和已有显式 entries 选择唯一业务 owner，再按该 owner 的 operators/prompts 声明发现定义；无明确引用或多个 owner 冲突时不猜测。嵌套 owner 工作区原匹配规则不变。

验收发现一个独立的底层兼容限制：Lance 对未精确定位的新 URI 会继续读取祖先 relocation 文件，当前受限预览因此可能拒绝访问。工作台预解析 URI 不能阻止 SDK 二次解析，本批不通过开放祖先目录或替换 SDK resolver 消除限制。真实新增流程验收使用已配置的精确输入/输出位置；不能据此声称任意新存储位置均可预览。证据为共享评审目录的 `lance-new-output-probe.json`；后续需在底层职责范围内提供明确的解析边界或已解析引用接口。

不为此修改引擎、SDK、通用算子实现、生产数据或其他产品分支；实际图片来源与质量定义属于业务输入，不由平台测试替用户决定。
