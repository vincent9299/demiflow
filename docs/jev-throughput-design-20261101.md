# JEV 单卡吞吐排查与优化

本轮只修改平台，不改业务输入、模型权重、精度或共享环境。只启动任务拥有的 GPU 0/1 服务；已有服务不重启，不 commit/push。开始时的脏文件快照在 `/tmp/demiflow-jev-bottleneck-20261101/baseline`。

## 测量与选择

先用同一实例的原生结果作为逐条基线，测 200 条不同长度业务输入，观察输入准备、lane 排队、共享/独占 gate 等待、原生 forward、图捕获和回放。使用正式默认缓存和捕获预算，避免从前一轮人为限制 32 次捕获的实验推导生产结论。阶段耗时有嵌套和并发，不能直接相加当端到端时间。

重点核查：缓存覆盖了多少不同形状、相同形状在不同 lane 的副本数、空闲 lane 的 miss 是否本可由另一 lane 的已有图处理。之后再选择改动，不以 GPU utilization 作为吞吐收益证明。

候选优化保持精确形状，不 padding、不合批。公共缓存/调度机制留在 `cuda_graphs.py`，JEV 原生执行及状态隔离留在 JEV backend。不能用固定形状绑定单 lane 或全局串行取代真正并行。对捕获、释放及原生 runner 的独占保护必须保留。

## 预算与验证

- 单模型进程，一张 GPU，两个 lane；HTTP 在途最多 4。沿用 4 GiB 图缓存、74 GiB allocator、输入和问题扩展上限。
- 输入文件最多 32 MiB，恰好 200 条，每条最多 1 MiB；每阶段最多 2000 请求、2/4 个客户端 worker。指标最多 128 个标签，每标签 4096 样本，形状元数据不超过缓存历史预算。
- 最多 12 个对照阶段；诊断及服务日志合计预留 256 MiB，端到端 journal/checkpoint 另按行数和字节预留、不覆盖历史证据。总实验超时 30 分钟，结束清理自有服务和锁。
- 先设计 review 和 CPU 回归，再 GPU 对照；使用同实例原生答案、token usage、完整浮点输出严格相等及既有 hidden 校验。不放宽容差，不把只对一组输入相等写成全模型证明。
- 对照交替顺序、相同输入/并发/预算；正式计时与重型 profiling 分开。缓存状态会影响结果，报告冷启动、预热和稳态，明确捕获数及命中率。
- 新公共策略须验证 FIFO、关闭/失败唤醒、缓存失效、资源释放和并行；优化只有端到端收益稳定且质量检查通过才保留。

## 初次设计 review

输入准备或重复 tokenization 可能只占小部分，先测量，避免将 CPU 微基准收益当作 GPU 吞吐收益。图池共享和 cuBLAS workspace 生命周期改动风险较大，不作为本轮首选。缓存亲和性不能引入无界等待、第二套队列或同形状永久串行；如不能满足这些约束，放弃该候选。

## 候选 review：按实际图副本统计需求

原策略按 shape 统计请求频率，却按 `(lane, shape)` 缓存。一个 lane 的热度会保护另一个 lane 的冷副本。改为观察、准入、淘汰统一使用完整缓存 key，不新增队列或模型特例，不增加历史条目上限。`min_observations` 相应指向每个可执行副本，捕获可能更晚；需要同时报告预热与稳态。两个 lane 各自频繁请求同一形状时仍可拥有两份图并行回放。

所有 backend 使用同一个缓存策略，三处调用传入已经存在的 key。模型执行、资源估计、FIFO 和 gate 完全不改。CPU 测试覆盖冷副本不能继承热副本频率。GPU 使用同一模型实例切换旧策略快照和候选缓存，每次排空后释放缓存，ABBA 共四块，每块同样预热 1200 条并测 600 条；原生 Dataset 200 条先生成严格基线。所有阶段使用实际 Dataset + journal + checkpoint 并校验重放。总 7600 条推理，12 个正式对照阶段；缓存从不同时驻留，仍以 4 GiB 为上限。

公共策略变更另用 32 条有界样本覆盖长短输入、多问题和不同 readout 数量，对 pplx、AMOS、d3 逐个做同实例原生 32 条 + 双 lane 288 条回归。沿用 `native_cuda_graphs.py`，每个进程最多 10 分钟、4 GiB 缓存、64 GiB allocator、16 个条目；关闭前一个进程后才启动下一个。它们验证输出和捕获/回放正确性，不用于宣称三个模型的吞吐提升。所有额外 GPU 回归都等 JEV 正式计时结束后再运行。
