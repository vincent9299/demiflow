# 模型服务第二轮 Review 与 GPU 实测

日期：2026-10-31。结论：修复平台实现与质量门槛漏洞；**pplx/JEV 候选合批不通过，生产合批保持关闭**。
这是实现者复验，不代表独立 reviewer 已签字，也不承诺不存在其他缺陷。

后续已完成 [原生根因对照与独立副本并行验证](model-services-rootcause-20261031.md)。
本文保留本轮历史结果；当前平台可通过 `replicas: 2` 在 GPU 0/1 真正并行执行，
不再局限于单副本串行。未通过质量门槛的原生合批仍关闭。

## 本轮修复

1. 独立 worker 启动时 `services/http.py` 遮蔽标准库 `http`，导致真实服务不能启动。
2. 整批异常对象被多个行共享，行级错误元数据可能串写。现在每行有独立异常和 journal 引用。
3. 聚合 token 超限误伤合法批次伙伴。现在拆成受预算约束的子批，再按行回填。
4. 最后一份 lease 关闭期间提前删除 registry，下一 action 可能撞上仍占用的 GPU。
   现在等待关闭完成；调用方取消不会取消已经开始的清理任务。
5. 质量证据只测部分批大小、漏答仍一致、重复样本凑数、未验证输入类型组合等漏洞。
   v2 要求 200 个不同输入、所有允许批大小、三轮伙伴、完整问题/选项响应、逐模式计数，
   并记录模态/问题/选项数的组合。模型文件签名加入证据身份，旧 v1 不再放行。
6. JEV 并发单条会触发 vLLM 内部合批，原先只限制显式 batch 路由不够。
   默认路径现在并发接收、有限排队、串行执行整个请求；只有验收模式或匹配的通过证据才放开。
7. d3 改为统一有界 HTTP worker 托管原生 D3/Decider，保留原生推理、媒体与读出，
   避免另用一个没有连接线程上限的 HTTP 服务。保留其可选 bearer 环境变量的认证语义。

职责仍是配置 → 部署 profile → 共用 HTTP 生命周期 → 原生适配器。行预算、journal、
重试和调度继续归现有算子，没有另造执行器、路由器或数据库。

## 测试条件

用户明确授权空闲 GPU 0/1；本轮只使用这两张 H100 80GB。GPU 2/3 不参与测试。
测试实例由 `demiflow.services` 启停，使用独立临时目录和端口。没有重启其他任务的服务，
没有修改已安装模型环境，没有写入 `/tmp/crosscheck2`、`/tmp/crosscheck3` 或业务数据。

使用本机已有权重和环境：pplx-decider 0.3.0、vLLM 0.31.0 / transformers 5.17.0 /
StartLux 1.1.0、amos-serve 1.0.0。原生精度、校准、attention 限制保持。

200 条测试输入包括：100 条已有身份样本，加上从旧评分中挑选相近分类分数的 100 个名称，
重新构造 2/3/4 选项、顺序变化、长短混合及多问题请求。后者测试协议和数值稳定性，
不是对原业务 triage 准确率的验收；旧分数相近也不保证新请求仍在决策边界。
本轮输入为文本，没有图片/视频质量认证。

候选批量：串行单条 200 条、4 并发单条 200 条、batch size 1–8 各 3 轮随机伙伴，
每个批大小 600 条，总计每模型 5200 条。概率绝对容差预先固定为 **1e-6**，标签必须一致。
显存是本部署进程树的采样值，不能当作捕获所有瞬时峰值；缓存驻留会影响阶段读数。

## 候选批量结论

* pplx：累计 10 次标签差异，5849 个概率比较超过容差，最大绝对差 **0.0558717373**。
* JEV：累计 7 次标签差异，4806 个概率比较超过容差，最大绝对差 **0.0294218973**。
  其中并发单条已经有 1 次标签差异、最大概率差 0.0287521087。
* 以上是跨轮次累计比较次数，不是不同错误样本数，也不是业务准确率下降的证明。
  它们已经足以否定“与单条等价”的验收条件；没有放宽门槛或自动发布通过证据。
* pplx 最快批大小为 3，相对并发单条约 **1.81×**；JEV 最快为 8，相对并发单条约 **1.43×**。
  若仅与串行比较，JEV 为约 2.73×。不能据此宣称质量与目标性能均达标。

另行启动 JEV 的 `VLLM_BATCH_INVARIANT=1` 实验，原生引擎明确拒绝：
`VLLM batch_invariant mode is not supported for GDN_ATTN.`
没有修改共享 vLLM/模型内核来绕过限制。

## 默认路径与算子回归

pplx、amos、d3 的原生单实例执行锁保留；JEV 默认新增请求执行锁。
并发单条提交仍然受支持，但单实例实际 forward parallel 为 1，不能把队列容量叫做计算并行。
需要跨副本的真实并行时应由独立模型实例提供；本轮没有新增自动副本路由。

默认路径 200 条串行/并发对比：pplx、JEV、amos、d3 的标签和概率差异均为零。
amos/d3 没有跨请求列表接口，保持 `batch=false`；没有把同一请求内部的问题合并冒充跨请求 batch。
amos/d3 的运行环境提示缺少优化版 `causal_conv1d`，使用正确但更慢的原生回退实现；本轮没有修改环境。

平台 CPU 回归 **181 passed**；最终新增边界复核 **44 passed**。两组有重叠，不相加。
一次整批异常测试依赖 50ms 内完成磁盘准备，在并行 GPU 测试期间未形成同一批；
改为编码后同步两行入队，修正测试时序依赖，保留“单次发送、独立行引用、不自动重试”的断言。

1k 行真实 `map_prompt_async` 测试通过，使用最终默认 JEV profile，concurrency=4、
queue_depth=4、SQLite max_requests=1000。输入为 100 条身份样本各构造 10 个独立请求，
用于规模/恢复 smoke，不冒充 1000 个独立语义样本的准确率评估。
首次得到 1000 条输出、1000 次请求和响应，HTTP/传输错误均为零；含冷启动与关闭耗时
191.39 秒。随后禁用 `DeploymentService.bind` 再跑全部 1000 行，0.60 秒完成，
输出一致、journal 请求数仍为 1000，证明没有启动模型或重复发送。
JEV 未返回逐行 usage，journal 的 usage_records=0；汇总中的 token 计数 0 不代表实际零 token。

结束后检查本轮服务进程和端口，GPU 0/1 显存均为 0 MiB；GPU 2/3 始终未被本轮配置使用。

* `run.py`、`smoke.py`：本次测试脚本；`final-code-sha256.json`：最终服务实现摘要。

候选失败报告产生于本轮中途修正前的适配器快照，不能作为最终代码的启用证据；
即使使用报告自身的身份，质量检查也明确拒绝这两份报告。
本地模型大文件签名使用路径/大小/时间，小型元数据增加内容哈希；它检测常规变更，
不能抵御恶意保留时间戳改写权重。显式权重 revision 仍应不可变。

初始 51 文件脏工作树中 48 个逐字节保留，其余 cli/systemone/pyproject 仅有此前授权增量。
原 `systemone.request_payload` 图片支持 AST 不变。本轮前另有完整 81 文件快照：
`/tmp/demiflow-review2-20261031T142809`。没有 commit/push。

未完成的验收是：合批质量与目标加速、图片/视频的真实质量覆盖、全新隔离环境下载安装，
以及业务 reviewer 的分布/准确率验收。不能把本次修复写成高性能合批功能已经全部通过。
