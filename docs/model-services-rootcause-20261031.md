# pplx/JEV 原生根因对照与独立副本并行

日期：2026-10-31。结论：**已复现的跨请求输出变化发生在原生执行链路，
不是 demiflow 请求转换、概率读出或批量回填造成。生产合批继续关闭；
新增独立 GPU 副本并行，两个模型均达到约 2× 吞吐，实测结果与原生单条完全一致。**

这是对 [第二轮 GPU review](model-services-gpu-review-20261031.md) 的后续核查。
这里的“原生问题”指当前模型库、算子、精度和调度组合没有满足批量数值不变性，
不等于模型权重错误，也不等于未来实现不可能安全合批。

## 1. 对照设计

沿用 200 条不同文本输入：100 条真实 identity 输入，100 条使用真实名称构造的
triage 输入；覆盖不同长度、2/3/4 个 choice、noul、多问题与临界概率。
它们不是 200 条人工标注准确率评估；图片与其他输入分布没有在本轮认证。
概率容差预先固定为 `1e-6`，标签必须一致；失败后没有放宽门槛。

测试只用用户授权的 H100 80GB GPU 0/1。原生探针绕过 demiflow 服务适配器，
副本测试则使用真实 `DeploymentService`、HTTP worker 和算子 runtime。
使用已有只读模型环境：pplx-decider 0.3.0 / Torch 2.14.0，
JEV 使用 startlux-decide 1.1.0 / vLLM 0.31.0 / Torch 2.13.0。
原始证据、探针脚本与临时 journal 在 `/tmp/demiflow-rootcause`。

## 2. pplx：直接调用原生 Decider

在同一模型进程中，直接调用 `Decider`，再与适配器调用相同的原生输入对照：

| 对照 | 标签变化 | 超容差概率项 | 最大概率差 |
|---|---:|---:|---:|
| 适配器单条 vs 原生单条 | 0 | 0 | 0 |
| 原生 batch=2 vs 原生单条 | 0 | 253 | 0.0558717373 |
| 适配器 batch=2 vs 同批原生调用 | 0 | 0 | 0 |
| 原生 batch=8 vs 原生单条 | 0 | 290 | 0.0444272632 |
| 适配器 batch=8 vs 同批原生调用 | 0 | 0 | 0 |

概率项数可超过请求数，因为一个请求有多个问题/选项。这一轮固定伙伴未翻转
标签，并不推翻前一轮三次随机伙伴已发生标签变化的证据。

进一步对 case 199 做控制变量实验：

- 重复原生单条调用，logits 完全一致。
- 同一个输入复制成两个、长度相同、目标不增加 padding，logits 仍改变。
  choice logits 从 `[13.375, 12.9375, 7.75]` 变成
  `[13.1875, 13.0625, 7.53125]`。因此不能仅靠按长度分桶消除变化。
- 单个输入只增加左 padding、不加入另一条内容，也改变 logits；本例右 padding
  没有变化。右 padding 只做诊断，未作为平台“修复”上线。
- 保持伙伴长度，只反转伙伴 token 内容，目标 logits 完全不变。
  这支持本例变化来自批维度/padding 的数值执行差异，而不是另一请求的语义串入。

全张量内核探针进一步显示：前两个 GDN 层的卷积输出、Q/K/V 在单条与等长重复
批次间完全一致，但门控参数 `g`/`beta` 出现差异；第二个 GDN 输出随之改变。
将捕获的同一份 Q/K/V/g/beta 独立送入 `torch_chunk_gated_delta_rule`，
B=1 与复制成 B=2 的输出完全一致。因此不能把本例直接归咎于 GDN 核心递推；
差异已经在门控输入产生。进一步捕获完整的归一化输入，前两层输入均逐元素
一致；固定这些输入，单独调用原生 `in_proj_a`/`in_proj_b`，仅将 B=1 复制成
B=2，便精确复现原来的投影差异。第二层两种投影最大差均为 0.0078125，
分别有 50 / 34 个元素不同。这将本例的起点定位到了原生 BF16 线性投影的
批形状相关数值变化，之后经门控和网络放大；没有进一步声称已定位具体
cuBLAS 算法或全部输入的唯一起因。完整数值见 `pplx-projection.json`。

证据：`pplx-native/report.json`、`pplx-kernel.json`、`pplx-kernel-isolation.json`、
`pplx-projection.json`。早期采样 token 的 module hook 没看到投影差异；
完整张量探针补足了这个盲区，不能将采样位置的零差异当作全张量不变的证明。
所有 hook/函数替换仅发生在临时诊断进程，没有改模型环境或平台推理路径。

## 3. JEV：直接调用原生 vLLM

只启动官方配方的 vLLM engine，使用模型自带 `jev_format` 与 `vllm_readout.json`，
直接访问 `/v1/completions`，不启动 demiflow SystemOne wrapper：

| 对照 | 标签变化 | 超容差概率项 | 最大概率差 |
|---|---:|---:|---:|
| 再跑一次原生单条 vs 原生单条 | 0 | 0 | 0 |
| 四个并发原生单条 vs 原生单条 | 1 | 190 | 0.0287521087 |
| 原生 prompt 列表 batch=8 vs 原生单条 | 1 | 139 | 0.0156199157 |
| 适配器重放同一份原始响应 vs 原生读出 | 0 | 0 | 0 |

最后一行同时断言适配器发出的请求 JSON 与独立构造的原生请求完全相同，
再将捕获的同一份原始响应交给适配器读取。这隔离了后端自身的运行差异，
避免将“先后两次请求输出不同”误判为适配器概率计算错误。

case 136 的两个原始 logprob 在单条下都是 `-0.6931471825`，概率各为 0.5；
相同输入复制成两条时，三次实验中一次原始 logprob 已经变成
`-0.6623854041` / `-0.7248854041`，概率变为 0.5156199157 / 0.4843800843。
变化在适配器读到响应之前已发生。原生 continuous batching 的实际调度不固定，
不能用一次“这个 batch 恰好相同”认定安全。

当前证据把责任边界定位到原生 vLLM/JEV 执行栈，尚未将所有变化唯一定位到
某一个 CUDA kernel。前次尝试的 `VLLM_BATCH_INVARIANT=1` 因 `GDN_ATTN`
不支持而失败，不能宣称打开一个开关即可保证该模型的质量。
证据：`jev-native/report.json` 与 `jev-native/native-recordings.json`。

另外启用官方 `STARTLUX_PREFIX_BIDIR_CHECK=1`、`_CHECK_REQS=16`，
对单条、长短混合、相同输入重复共 7 个原生序列完成检查。插件逐请求计算
显式 prefix mask 的 FP32 注意力参考，所有调用通过其原生精度断言。
这为所测请求的注意力隔离提供补充证据；该检查使用 kernel 级 BF16 误差界，
**不等于**最终概率 `1e-6` 质量门槛通过，不据此重新开启合批。
日志：`jev-check-service/deployments/ceaa97bff87121f7603337554b7a669e/engine.log`，
原始响应：`jev-check-responses.json`。

## 4. 真正并行：两个独立模型副本

保留每副本原生单条路径，GPU 0/1 各加载一个模型。新增约束明确的
`ReplicaService`：最多 16 个实例，每次请求从服务租约取得一个空闲端点；
一个实例同时只接纳一次调用，另一实例可以独立 forward。

这复用原 `ServiceGroup` 的启动、失败回滚和清理，不增加 HTTP 代理、
模型执行器或业务调度器。Dataset 仍负责行并发/预算/重试/journal。
端点只随本次请求返回，不修改共享 base_url；复制数不改变业务请求键。
`start/status/logs/stop` 复用相同组件列表，persistent 模式沿用原有跨进程请求锁。
空闲选择发生在调用进程内，不声明集群级全局最优负载均衡。

原完整 prompt/agent YAML 内的 `model.deployment` 增加：

```yaml
gpus: [0, 1]
replicas: 2
request_concurrency: 4
```

算子 `concurrency >= 2`，不设置 `systemone_batch`。pplx/JEV 没有通过的 batch
证据；默认与当前实测配置均不放行合批。多副本还显式拒绝复用单设备 batch
证据，防止绕过已验证设备范围。省略 replicas 不改变已有 TP 部署的语义。

## 5. GPU 服务层性能与一致性

两个副本分别跑 200 条单条，再将相同 200 条输入随机混合成三轮共 600 条，
以两个并行调用跑副本池。下面的单副本基线取两份副本中吞吐较高者。
所有模式均与前述独立原生单条基线对照，而不只是互相比对适配器。

| 模型/模式 | 吞吐（条/秒） | p50（ms） | p95（ms） | 单 GPU 显存采样峰值 |
|---|---:|---:|---:|---:|
| pplx 单副本 | 10.56 | 91.23 | 141.17 | 51,025 MiB |
| pplx 双副本 | 21.54（2.04×） | 89.91 | 140.42 | 51,025 MiB × 2 |
| JEV 单副本 | 13.40 | 66.27 | 199.33 | 65,065 MiB |
| JEV 双副本 | 27.28（2.04×） | 65.65 | 187.73 | 65,065 MiB × 2 |

两模型各自的两轮单副本和三轮并行测试全部 **标签变化 0、概率差 0**。
pplx 600 次路由分布为 302/298，JEV 为 303/297；最大同时 HTTP 调用数均为 2。
pplx 73 次采样中 72 次两卡同时有 GPU 活动；JEV 55 次中 54 次。
因此这里测到的是独立执行并行，不是单实例排队。显存采用整张卡采样，
测试期间没有其他 GPU 任务；采样不保证捕获所有瞬时峰值。

服务层计时不含模型启动、Dataset 与 journal。pplx 双副本启动约 60 秒，
JEV 约 243 秒；现有组合服务按顺序启动，未优化冷启动。吞吐收益来自两份
模型的独立执行，代价是两份完整权重/缓存显存，并非单卡合批加速。

证据：`pplx-replicas/report.json`、`autotrust-jev-replicas/report.json`。

## 6. 算子、恢复与 CPU 回归

两个模型各跑 1,000 行 identity runtime smoke，保留 1,000 次逐行请求/响应，
HTTP/transport 错误均为 0。停止全部实例后，禁止 `DeploymentService.bind`，
再重放 1,000 行：输出完全一致，无新增请求、无 GPU 启动。
JEV 实际并发容量为 4，运行 34.39 秒，停机重放 0.49 秒。
pplx 首次 runtime smoke 脚本漏设客户端容量，仍使用默认单连接，93.66 秒；
这次只作为功能/恢复证据，不能当作端到端并行性能证明。

随后补跑真实 `DataAPI → map_prompt_async → checkpoint` 的 pplx 1,000 行链路，
`replicas=2`、`concurrency=4`、`queue_depth=4`，不使用手写 runtime 容量。
包含两个模型冷启动与关闭总计 113.06 秒；完整记录 1,000 请求、1,000 响应、
1,000 usage、210,120 input tokens，错误为 0。包含冷启动阶段的 305 次采样中
128 次两卡同时工作，确认 Dataset 路径确实并行。停止模型、禁止 bind 后再次
运行同一 Dataset，0.74 秒重放全部 1,000 行，逐行结果一致，请求总数保持 1,000。
证据：`pplx-dataset/result-0.json`、`result-1.json`、`calls.sqlite`。

CPU 相关回归 189 项通过；最终端点上下文兼容性修正后补测 27 项通过
（有重叠，不能相加成独立用例数）。覆盖取消归还副本、关闭唤醒等待者、
启动失败回滚、persistent 保留既有实例/清理新实例、GPU/端口分配、
单设备 batch 证据拒绝、逻辑行身份、实际端点路由及无启动重放。
原第三方 request_slot 上下文返回非字符串对象时仍按旧行为处理。

CPU 报告：`cpu-regression.xml`、`cpu-final.xml`。

## 7. Review 结论与边界

- 未更改模型权重、原生精度、校准、提示词或安装环境来换取吞吐。
- 合批失败继续关闭；JEV 同一执行实例的跨请求 continuous batching 同样受约束。
- 真并行使用独立副本，复用现有生命周期和算子，不新增第二套行调度。
- 测试证明上述文本样本及当前版本/设备条件一致，不是所有输入的数学证明，
  也不是模型准确率的重新认证。图片、不同硬件/版本需独立验证。
- GPU 2/3、业务数据、其他打分服务与 `/tmp/crosscheck2`、`/tmp/crosscheck3`
  未参与运行。未 commit/push。任务前未提交改动按快照保留。

本轮结束已关闭测试自有实例，GPU 0/1 显存回到 0 MiB。修改前快照为
`/tmp/demiflow-rootcause-baseline-20261031T151225`：82 个既有脏文件中 70 个
字节未变，12 个按本任务修改，新增 3 个文件；原 `systemone.request_payload`
与实现前快照的 AST 一致，图片 state 支持保留。修改摘要与 SHA-256 见
`/tmp/demiflow-rootcause/final-source-review.json`。
