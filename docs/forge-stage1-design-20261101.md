# Forge 第一阶段架构与方案设计

日期：2026-11-01。状态：用户已通过，第一阶段实现已落地；验收见 [验收记录](forge-stage1-acceptance-20261101.md)。目标仓库：demiflow。

Forge 的目标是让开发者在统一工程标准下，依据当前平台的真实能力交付业务 Pipeline。原生 Python 与 Dataset 表达流程，Forge 发现接口、检查约束并管理证据。业务增加阶段或改变组合，不应要求修改 Forge 核心。

第一阶段建立工程标准、平台能力目录、平台快照和差异检查。本设计通过用户 Review 后才进入实现。每个后续阶段同样先交付架构与详细方案，Review 后实现、验证和交付。

## 1 阶段范围与交付

后续阶段已按工作区、数据表和可见组合重新规划，见 [阶段调整提案](forge-roadmap-20261101.md)。下表保留第一阶段通过时的分阶段安排；第一阶段实现与验收不变。

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 第一阶段 | 独立工程标准、动态接口目录、平台身份、快照及差异检查 | 接口信息来自代码；平台变更可识别；没有流程拓扑限制 |
| 第二阶段 | 原生业务入口接入、需求与实现分离、派生 Manifest | 多种业务组合不要求改 Forge 核心；统一目录与职责 |
| 第三阶段 | 静态与行为验证、Review、Freeze、受管运行接入 | 证据绑定实际实现；执行使用已验证快照；明确检查覆盖 |
| 第四阶段 | 题目生产的离线业务验证及获授权的真实 canary | 完整分母、独立题审、有限修订、失败与完成条件 |

第一阶段的可用结果是：开发者可以查询当前平台接口，保存明确范围的平台快照，并判断它是否已经变化。新能力此时尚不替换旧项目的执行协议，也不宣称旧 Verify、Freeze 已完成迁移。

本阶段不定义新的 DAG 语言，不实现业务流程提取、模型执行、服务启动或生产运行。正式入口形式和目录细节留到第二阶段设计；这一阶段不以旧三节点 Definition 预先限制它们。

## 3 架构与所有权

```text
平台维护的公开入口 ─→ 只读接口发现 ─→ 当前平台目录
当前包源码与环境信息 ─────────────→ 平台身份
版本化工程标准 ─────────────────→ 标准身份
                                      ↓
                                 平台快照
                                      ↓
                      与当前事实比较并输出结构化差异
```

| 内容 | 权威来源 | Forge 的职责 |
| --- | --- | --- |
| 工程标准 | 随 Forge 发布的版本化标准 | 维护统一规则、规则来源和检查覆盖 |
| 平台接口事实 | demiflow 公开代码及原生配置解析器 | 自动提取、定位来源、保存版本 |
| 业务需求 | 用户确认的需求及业务规范 | 后续绑定，不能由候选实现自行改写后通过验收 |
| 具体流程 | 原生业务代码及配置 | 后续提取使用事实；不生成另一份执行语言 |
| 验收证据 | 对明确快照的检查、测试和 Review | 后续管理有效性与失效原因 |

Forge 独立运行，不读取 DemiForge、Demiurge 或 demiwtg 配置。原 DemiForge 的授权范围内接口反射机制仅作为设计参考。

### 3.1 工程标准

新增独立标准来源，统一规定正式入口与职责、显式数据流、模型调用边界、固定输入与完成条件、资源与恢复要求、证据绑定。标准不包含 `nodes` 列表、唯一 operator 数量、固定业务阶段或复制的 Dataset 参数表。

每条规则至少标识规则 ID、版本、要求、适用范围及验证方式。验证方式区分静态检查、行为测试和语义 Review；第一阶段只描述与实现本阶段覆盖的检查，其余标记为后续接入，不能因规则已写入就声称已经拦截。

标准格式、标准内容版本、平台代码版本分别记录。普通业务组合变化不升级标准；接口签名变化更新平台快照；规则含义变化才修订标准版本。

## 4 动态接口发现

### 4.1 发现范围

初始发现入口为 `demiflow`、`demiflow.data`、`demiflow.operator_llm`、`demiflow.agent`、`demiflow.inference` 和 `demiflow.services`。这是平台命名空间的边界，不是逐算子的白名单，也不表示已经覆盖整个 demiflow 包的全部公开能力。

在这些入口中按实际 `__all__` 枚举导出对象，继续枚举公开类的公开成员。新增导出函数或 Dataset 公开方法应自动出现在目录，不修改 Forge 方法名列表。新增公共命名空间由平台明确开放，业务项目不能借配置任意扩大模块导入范围。

`demiflow.agent` 当前没有 `__all__`。实现时为这个现有公开模块补充 `AgentConfig`、`load_agent_config` 的显式导出；不把所有非下划线 import 都当作公共接口。其他尚未纳入的对象库、检索等命名空间显式报告为范围之外，后续按实际使用扩充入口。

### 4.2 提取规则

1. 仅解析受信任的平台安装或当前源码根。业务项目目录不进入检查进程的模块搜索路径；导入后核对模块及定义对象来源，拒绝同名模块遮蔽。
2. 公共入口以 `模块:对象路径` 为接口 ID，例如 `demiflow.data:Dataset.map_prompt_async`。导出路径与定义位置分别保存；别名保留，不能以函数名相同合并不同对象。
3. 记录函数、类、方法和属性的类型。普通方法、静态方法、类方法及继承成员分别识别；属性只检查描述符，不求值。继承成员保留真实 owner，外部 owner 绑定对应依赖身份。
4. 读取真实签名、完整公开文档、定义模块和相对路径。注解不执行字符串求值；默认值不调用任意对象的 `repr`。非字面量默认值显示类型与来源，语义变更由实现摘要捕获。
5. 不构造业务 actor、服务或模型对象，不调用发现的函数、property getter、部署准备或健康检查。受信任模块导入仍会执行模块顶层代码，导入纯净性需要专项测试；子进程本身不是安全沙箱。
6. 缺文档、无法检查的签名、可选依赖缺失、未支持描述符或导出对象无法解析，均形成诊断。不能静默删除对象，也不能伪造完整签名。

接口文档保持原文和完整含义。超过单项上限时报告超限，不截断后标记为成功；CLI 列表只显示摘要，详情命令返回完整对象记录。

对象类型决定字段是否适用：函数和方法记录调用签名；属性记录读取契约；异常类型等声明对象不强制拥有可调用构造签名。每条记录分别标记签名、文档和来源字段为已获取、缺失或不适用。字段确实缺失可以完整记录；无法枚举模块、无法确定来源或检查被中断，才意味着范围检查未完成。后续使用某个接口时，再检查它所需的字段与语义是否充分。

### 4.3 原生语义信息与缺失项

签名只能说明调用形状，不能推断函数是否有网络、模型或写入副作用，也不能推断资源硬上限。

目录预留原生配置格式、解析器引用、效果说明和后端约束的来源字段。已经有机器可读信息时引用平台原生声明；只有文档时保留文档，不用文本匹配自动授予执行能力。缺失项标记为 `unknown`，不得默认解释为纯计算或可运行。

第一阶段不批量修改 Dataset、服务或模型代码补注解，也不为每个 API 在 Forge 手工再写一份契约。后续需要机器可检查语义时，由对应平台模块维护唯一声明，并在其原生测试中验证。

### 4.4 目录事实与执行许可

目录表达 `discovered`、`inspection_complete` 和诊断；工程规则的允许状态、运行环境就绪状态以及业务验证覆盖属于后续独立判断。

例如，发现 `DeploymentService` 说明当前代码公开了这个类，不代表允许启动 GPU 服务；发现 `map_prompt_async` 也不代表本次任务授权真实模型请求。`unknown` 不可自动转换为 allowed。

## 5 平台身份与快照

### 5.1 身份组成

| 身份 | 内容 | 变化时的解释 |
| --- | --- | --- |
| `standard_digest` | 工程标准、规则版本和本阶段检查覆盖声明 | 验收标准已变化 |
| `catalog_digest` | 选定范围内接口 ID、签名、文档、owner 和诊断 | 公开接口或可检查性已变化 |
| `platform_source_digest` | demiflow 包内受管文件的相对路径与内容，包括 Forge 自身、内部实现和打包资源 | 平台或检查器实现已变化 |
| `environment_digest` | Python 实现与版本、当前分发身份、声明依赖及已安装版本和可用元数据 | 检查环境已变化 |
| `snapshot_digest` | 格式版本、发现范围、上述身份、完整性状态和预算配置 | 本次快照的整体身份 |

时间戳、临时目录、机器绝对路径和日志位置属于诊断信息，不进入语义摘要。排序、编码和缺省值处理统一；同一内容在同一环境下重复提取必须稳定，移动等价源码目录不应单独改变身份。

不使用 Git HEAD 代替内容摘要。未提交、未跟踪以及未改变版本号的源码修改同样必须被识别。

平台来源分为当前源码和已安装分发两种。源码模式核对当前包路径及其所属 `pyproject.toml`，将版本、依赖声明和打包声明纳入身份；已安装模式核对包与分发元数据的对应关系。不能把源码 checkout 的内容与另一份同名已安装包的元数据混合。遇到来源歧义则报告 incomplete，不按当前工作目录猜测。

### 5.2 平台源码边界

第一阶段采用保守的整个 demiflow 包内容摘要，覆盖私有模块与 vendored 资源。排除 Python 字节码和明确的缓存目录；仓库的 datasets、runs、benchmarks、其他仓库和模型权重不在包内容范围。

不依赖脆弱的 import 推断声称已经求出完整执行依赖闭包。无关包内文件变化也可能导致 stale，这是第一阶段选择的保守行为。将来需要缩小失效范围时，应通过独立设计和依赖测试验证。

扫描与哈希使用有界目录遍历和流式读取，拒绝符号链接、特殊文件、路径逃逸和超限；哈希前后检查文件身份及长度、修改时间。生成目录前后分别取源码身份，发生变化返回 `source_changed`，不发布混合快照。此机制检测普通并行编辑，不把活动工作树称为不可变运行包；第三阶段运行使用冻结副本。

### 5.3 环境身份的保证范围

第一阶段读取分发元数据、声明依赖闭包及环境中相应包的版本；存在时记录 METADATA、RECORD 等文件摘要。依赖条件按当前 Python、系统和明确启用的 extras 求值，不扫描与本平台无关的整个环境。可选依赖缺失如实记录，不自动安装、下载或启动外部服务。

direct_url 只提取规范化的分发来源、制品哈希及 VCS revision；本地安装路径属于诊断信息，不把原始文件整体哈希纳入可迁移身份。元数据正文、URL 凭据及认证参数不输出。规范化规则参与格式版本，不能通过删除有语义的来源差异使两个环境被误判相同。

环境盘点不能证明同版本依赖包的每个已安装文件都未被修改。快照因此显式记录 `dependency_assurance=metadata_only`。第三阶段在运行身份设计中绑定并校验实际环境制品，不能把本阶段的元数据盘点当成完整运行环境认证。

### 5.4 快照结构

拟定格式名为 `demiflow_forge_platform_snapshot_v1`，与旧 `demiflow_forge_contract_v1` 分开。字段结构如下，正式 schema 在实现时与本设计一起核对：

```text
format
scope                  # 实际检查的公开入口及发现规则版本
standard               # 工程标准身份
catalog                # 接口记录、来源、完整性和诊断
platform               # 包文件清单与平台内容身份
environment            # Python、依赖盘点与 assurance
limits                 # 实际生效的检查预算
digests                # 分项及整体摘要
provenance             # 时间和位置等非语义诊断
```

快照只保存接口与身份信息，不保存凭据、模型输入、生产数据或环境变量值。声明文件内的非敏感环境变量名称可以作为接口文档的一部分。

摘要用于一致性与漂移检查，不是防篡改签名。读取快照先验证结构和自身摘要，再与当前可信来源比较。

## 6 差异与失效判断

差异按可解释的类别输出：接口新增、删除、签名变化、文档变化、owner 变化、平台文件变化、标准变化、环境变化、检查完整性变化。

状态固定为：

| 状态 | 含义 |
| --- | --- |
| `current` | 检查范围完整，内容及环境盘点与快照一致 |
| `stale` | 已发现明确差异，需要重新生成快照和受影响的验证 |
| `incomplete` | 依赖缺失、检查不可完成或资源超限，无法得出一致结论 |
| `invalid` | 快照格式、摘要、来源或路径不合法 |

`current` 只证明平台快照在声明保证范围内一致，不表示业务测试通过或允许生产运行。存在差异且还有未检查项时仍保留全部诊断，并以 `incomplete` 表达不能完成比较；不能输出 current。

接口新增也使当前整体快照 stale，不自动将新增能力加入已经 Review 的授权范围。重新绑定是显式动作，不修改旧快照或旧证据。

第一阶段提供可供后续生命周期使用的比较函数和 CLI。旧三节点项目的 check、review、freeze、run 仍使用原协议；其证据不会被悄悄改写或被宣称已使用新平台身份。第二阶段设计绑定点，第三阶段完成所有门禁接线。

## 7 接口与命令

拟新增 `demiflow forge platform` 命令组，不占用或改变旧命令含义：

| 命令 | 行为 |
| --- | --- |
| `platform list --json` | 分页列出接口 ID、类型、来源和诊断，可按公开模块及名称筛选 |
| `platform show ID --json` | 返回一个接口的完整签名、文档及来源 |
| `platform snapshot --out FILE --json` | 生成当前完整快照，只创建新文件，完成后原子发布 |
| `platform check FILE --json` | 只读比较快照与当前平台，返回状态和结构化差异 |

发现范围可以通过重复的 `--module` 参数从平台已开放入口中选择，默认使用第 4 节的全部入口。范围写入快照；check 使用快照原范围，不通过缩小范围获得通过。

list 和 show 可以展示带诊断的局部结果。snapshot 遇到范围检查未完成时不发布正式文件，输出诊断；不能将局部结果写成完整快照。已确认的缺文档、签名不适用或缺少副作用机器说明可以作为真实状态保存，不能被解释为该接口可执行；模块无法解析、来源不明和超限等情况影响 inspection_complete。

成功退出 0；stale、incomplete、invalid 及检查失败退出 1；CLI 参数错误退出 2。JSON 结果与诊断不混入子进程日志。check 不启动测试、不修改快照、不刷新项目绑定。

内部提供三个核心调用边界：发现目录、构建快照、比较快照。平台根与已开放命名空间由受信任工具确定，不接受业务代码传入任意 import 目标。

## 8 资源与检查进程

以下为首轮实现默认预算，超限明确失败，不隐式扩大。测试使用更小预算触发同一边界。

| 对象 | 默认上限与处理 |
| --- | --- |
| 包文件扫描 | 8,192 个目录项、32 层深度、单文件 32 MiB、总内容 128 MiB |
| 依赖盘点 | 512 个分发、单份元数据 8 MiB、元数据累计 32 MiB |
| 接口目录 | 2,048 个对象、每类最多 512 个成员、继承检查最多 32 层 |
| 单项记录 | 完整文档 256 KiB、规范化签名 32 KiB |
| 整体输出 | 目录累计 16 MiB、快照累计 32 MiB |
| 检查子进程 | 单次总时间 60 秒、并发 1、stderr 累计 1 MiB |
| CLI 展示 | 列表默认 50 项、最多 200 项；show 按单项上限；差异分页且保留总数 |

检查使用独立进程、最小环境、禁写字节码和有界 stdout/stderr。先限制输入与累计大小，再解析或序列化；超时、异常及取消回收本次进程组和未发布临时文件。

包文件采用分块哈希，不读入完整内容。目录记录与序列化副本均计入内存估算；上述编码字节上限不等于进程 RSS 硬限制。第三方模块导入的原生分配不由目录字节预算覆盖，依赖超时及环境既有保护，不宣称本阶段提供 OS 资源沙箱。

默认不复用跨进程缓存来判断 current。一次命令内同一源码文件可以共享哈希结果；跨调用精确扫描，避免 mtime 缓存漏掉同尺寸或同时间戳改动。

## 9 实现模块与变更范围

| 位置 | 拟承担的职责 |
| --- | --- |
| `forge/standards.py` 及打包标准资源 | 独立工程规则及覆盖声明，脱离旧 nodes 契约 |
| `forge/platform.py` | 公开对象发现、别名与 owner、签名和文档记录 |
| `forge/platform_worker.py` | 受限检查进程的固定协议，不执行候选业务程序 |
| `forge/platform_snapshot.py` | 内容身份、环境盘点、快照校验与结构化差异 |
| `forge/platform_environment.py` | 依赖声明和分发元数据盘点；从快照模块拆出单一职责，不新增扩展框架 |
| `forge/platform_cli.py` | 四个命令及分页、退出码、输出处理 |
| `forge/cli.py` | 注册新的命令组 |
| `agent.py` | 仅补充现有公开对象的 `__all__` |
| 测试、Forge 文档和打包配置 | 边界用例、命令说明和新标准资源分发 |

尽量复用现有原子 I/O、错误格式和有界哈希思路。测试进程与接口检查进程协议不同；共用进程控制部分前先检查其行为，不为了复用而改变现有 pytest 调用语义。

不改动 Dataset、模型客户端、账本、模型服务和性能实验。若发现必须修复的平台公开边界，先提交具体证据及对本设计的变更，再纳入本阶段范围；不顺手修改并行任务。

第一阶段仅为旧三节点实现增加并列的发现基础，不为旧格式构造长期兼容框架。旧源码、例子和证据的迁移或归档在第二阶段方案中明确。

## 10 验收用例

| 类别 | 必须覆盖的行为 |
| --- | --- |
| 动态发现 | 在受控平台 fixture 新增公开方法，不改 Forge 列表即可发现；私有对象不被自动开放 |
| 导出与别名 | 别名定位同一 owner；同名不同对象不合并；继承成员和 property 不被执行 |
| 参数与文档 | 参数、默认值及完整文档变化被识别；非字面量默认值不调用自定义 repr |
| 原生配置引用 | Prompt Pack 与 Agent 配置入口来自当前代码；目录不维护第二份参数 schema |
| 包内实现漂移 | 只修改私有执行模块、Forge 检查器或包内资源，也必须返回 stale |
| 工作树身份 | 未提交修改及新增文件被识别；生成期间文件变化不发布快照 |
| 环境盘点 | Python、已安装依赖版本或元数据变化被报告；可选依赖缺失可诊断且不自动安装 |
| 确定性 | 相同内容重复提取摘要一致；绝对目录和时间变化不制造内容差异 |
| 来源边界 | 同名模块遮蔽、导出来源异常、符号链接及路径逃逸被拒绝 |
| 检查副作用 | fake 服务、构造器、getter 和敏感调用探针证明发现不触发执行；不使用真实模型或 GPU |
| 资源与失败 | 小预算触发目录、文件、文档、输出和时间上限；失败无半写快照，无遗留本任务进程 |
| CLI 与打包 | JSON、分页、退出码、独立安装后的目录查询和快照检查一致 |
| 既有行为 | 现有 Forge 25 项聚焦测试与相关 CLI 测试保持；旧门禁未被静默替换 |

测试中的平台模块为测试自有可信 fixture，通过测试内部依赖注入提供；不把任意模块导入入口暴露给生产 CLI。

第一阶段验收只证明目录、身份和差异检查。第二阶段用多种原生流程验证组合能力；第三阶段验证模型与输出副作用之前的策略检查，以及实际 Verify、Review、Freeze、Run 对新身份的完整绑定。

## 11 实施顺序与阶段完成条件

设计 Review 通过后按以下顺序实施，每一步使用对应测试锁定行为：

1. 定义独立工程标准、目录记录和快照格式，明确 unknown、incomplete 与 stale 的区别。
2. 实现公开导出发现和检查子进程，先通过无副作用、别名及完整文档用例。
3. 实现平台内容摘要、环境盘点和确定性快照，验证私有模块及并行编辑变化。
4. 实现结构化差异、CLI、打包及命令文档。
5. 完成本阶段边界测试、既有 Forge 回归和独立安装验证，交付实现差异与剩余限制。

完成条件是：开发者能从独立安装的 demiflow 查询真实接口，生成明确范围的完整快照，发现公共和内部实现漂移；检查没有触发模型、服务或生产 I/O，且现有工作和旧证据保持。

本阶段交付后再提交第二阶段架构与方案。第一阶段设计通过不代替后续阶段的设计 Review，也不授权真实模型、共享服务或生产数据运行。

## 12 本次 Review 的关键决策

1. **第一阶段只建设契约来源和身份基础。** 原生流程接入、完整生命周期与业务 canary 分阶段完成。
2. **自动发现公开对象，显式限定平台命名空间。** 方法和参数来自代码，业务方不能任意扩大 import 范围。
3. **平台事实与执行许可分开。** 缺少可检查语义时保留 unknown，不按名称猜副作用。
4. **先采用整个平台包的保守内容身份。** 接受较宽的证据失效范围，优先避免私有依赖变化漏检。
5. **准确标记依赖保证范围。** 第一阶段盘点元数据，第三阶段再完成实际运行制品的校验。
6. **第一阶段不改变旧项目门禁。** 新快照与旧三节点契约清楚区分，后续显式接入和迁移。
