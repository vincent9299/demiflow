# JEV 正式执行后端设计与复核

承接 `model-runtime-latency-review-20261101.md`。只改平台工作树；不修改既有模型
安装环境、权重或服务，不 commit/push。验收使用自有 GPU 0/1。

## 边界

优化配置使用一个受托管的 HTTP worker 和一个进程内 vLLM engine，共享一份权重。
原生 JEV HTTP 配方继续保留。协议的格式化、校准与 usage 不另造语义。模型内部
状态隔离和已定位的 FlashInfer 修复仅在固定版本的 JEV 后端中实施；公共执行层
只负责原有 FIFO lane、缓存、工作区、捕获与关闭，不增加 RPC 请求队列。

冷输入、图外输入及周期质量对照由唯一原生线程执行，使用同一原生配方。模型
ForwardContext 是全局对象，原生调度和图捕获必须取得独占门；通过检查的图才可
在固定 lane 上独立重放。`batch=false`，不拼接请求，不把两个 GPU 副本当作单卡
并行。图禁用时如实降低实际并行能力。

## 所有权与预算

- 服务限制 HTTP 载荷与 max_inflight；编码前限制 JSON 字节/问题展开量，编码后
  检查每个问题和整行 token 预算；超限拒绝，不能截断。
- 各 lane 独占 GDN state、KV、输入、Plan 和读出索引；只共享权重。状态按配置的
  最大图长度提前计算字节后分配，单 lane 状态上限 1 GiB。所有图共享其 lane 的
  长寿命状态，同一 lane 不并发，避免每个形状都复制完整 KV/state。
- 静态元数据/输入复制在分配前计费，单条上限 128 MiB。图缓存复用既有条数、
  字节、捕获次数/时间与热度策略，图使用私有池，淘汰时先排空 GPU。
- 图内使用到的读出索引、静态张量必须活到图销毁。只允许固定数量的 stream 和
  线程。cuBLAS 工作区必须在各图池内，不能清除原生 vLLM 图仍在使用的全局工作区。
- JEV 的 allocator 默认预算 74 GiB（仍须留至少 2 GiB 设备余量），缓存 4 GiB；
  vLLM 自有缓存、lane 状态和工作区均计入实际余量。该上限不涵盖驱动/全部第三方
  分配。不能以提高预算掩盖泄漏；不足时拒绝或回退，CUDA 执行错误停止接单。

## 质量与开放条件

首次捕获和周期检查比较原生有效 hidden state 与 processed logprob，要求精确
一致；失败不返回图结果，清理/禁用图。动态 token 复制、不同请求同形状、冷热
混合、淘汰后重建、短输入原生布局、选项数量及多问题均纳入回归。

原生数值漂移与并行 scratch 冲突分别审计。启动数值配置/依赖必须进入执行身份；
不得把新启动的原生结果自动解释成与历史基线一致，不重新写旧基线。历史触发
仍需独立控制变量证据。最终报告明确已解决项、可复现机制及证据局限。

发布到工作树前先跑 CPU 契约和边界，再跑完整服务的单条/并发零容差对照、不同
启动、GPU kernel 重叠、显存/缓存边界、质量故障、journal 和托管清理。验证前
不会把临时探针直接宣布成已完成的服务。
