# DemiFlow 发版规范

状态：正式规范，自 2026-11-19 真人确认起生效。适用于所有会话、开发者、集成者与服务负责人。
本文是版本、分支、工作树、验收、发布与归档的唯一现行规范；历史日期版与共享目录中的草案只作来源记录。
最新真人指令优先；已有明确授权继续有效，不因本文重复申请。修改本规范也须走隔离任务分支及合入闸。

**固定流程：最新 main → 隔离任务分支 → integration 合流验收 → main 定版 → demiflow/ 更新正式代码 → GitHub。预览换版单独执行。**

本规范约束实际操作，不表示所有步骤已有自动化。`merge_gate.py`、回归回执和已知状态工具分别提供证据；管理者仍须核实差异、来源、权限与服务依赖，不能把“脚本退出成功”当成全部条件满足。

## 1. 目录与职责

以下路径相对工作区 `/yzp/zhaozy/yangzepeng/0905/`，Git 仓库根是其中的 `demiflow/`。

| 位置 | 检出与用途 | 边界 |
|---|---|---|
| `_demiflow/worktrees/<任务分支名>` | 从最新本地 `main` 建任务分支，开发、测试、交付 | 一个任务一个树；不能复用别人的树 |
| `_demiflow/worktrees/integration` | `integration`，唯一合流与验收线 | 只合并任务分支，不直接开发或直接提交修复 |
| `demiflow/` | `main`，正式代码目录 | 不开发、不跑测试；仅管理者执行已验收版本的快进落位 |
| `_demiflow/worktrees/preview` | 游离检出固定的 `preview-…` 标签 | 只运行服务；合并、推送不会自动切换它 |
| `_demiflow/shared-review/` | 交接、发布记录、证据索引 | 不替代已提交源码或仓库现行规范 |
| `_demiflow/archives/` | 清理前的内容与恢复材料 | 没有明确授权不删除 |
| GitHub `origin` | `main` 与明确列出的发布标签 | 外部副本；不推本地归档引用 |

管理者负责 integration、main、两道闸、发版记录、推送与清理；当前为 GPT 总控。
任务负责人只写自己任务范围；复核者在自己的检出独立核验，当前为 Claude。
服务负责人负责排空、备份、换版和实站检查。这些角色可由用户重新指定；交接必须写明实际负责人、分支、提交和未完成项。

## 2. 分支与工作树

- 长期分支只有 `main`、`integration`。任务名为 `<谁>/<领域>/<主题>-<年月日>`，例如 `gpt/docs/release-rules-20261119`。领域为 engine、sdk、workbench、forge、test、docs、infra 等。禁止 `main/…`、`integration/…` 前缀。
- 新任务从最新 `main` 开始。不要为了获得其他未发布改动直接改从 integration 起步；确需依赖另一任务时，由管理者明确依赖的提交与交付次序。任务分支命名中的日期不代替基线提交。
- integration 只用 `git merge --no-ff` 接受交付，保留真实提交历史。不用 cherry-pick 或重新实现冒充合入。纠错在任务树完成后重试合并。
- 交付必须包含共享仓库内可解析的分支、完整提交号、范围、验证命令与证据。独立克隆内的提交由管理者先 fetch 成本地任务分支；只有口头说明不算交付。
- 不新建长期备份分支，不用 stash 保存新工作。自己的半成品可提交为 `wip:`；不能擅自提交其他会话的 dirty/staging。临时保存用 `refs/archive/<年月日>/…`，不使用需删除的发布标签。
- 已合入、验收完成且无进程/开发依赖的任务树与分支，在本批收尾归档移除。超过三天未交付的由负责人说明继续、更新基线或归档；时间本身不授权删除活跃任务。
- 一树一分支，路径原则上使用完整分支名。既有别名路径必须记录映射，不为改名搬动在线服务。`/tmp/demiflow-<谁>-<用途>` 只用于短期游离检出的比较/试合并，用完清理；跨日任务记录负责人。
- 运行测试要显式绑定实际工作树及私有资源域，进程内断言 `demiflow.__file__` 位于本树。不要依赖 editable 安装或裸 `pytest` 恰好命中正确目录。私有数据放 `/tmp/demiflow-*`，不复用生产资源账本。

## 3. 版本与标签

| 标识 | 使用时机 | 目标 |
|---|---|---|
| `main-YYYYMMDD-N` | 每次 main 定版前进 | 本次通过发版判定的集成提交 |
| `vX.Y.Z` | 用户决定发布产品版本 | 已有 main 定版标签的同一个提交 |
| `preview-YYYYMMDD-N` | 服务负责人实际切换预览版本 | 预览要启动的已定版提交 |
| `refs/archive/YYYYMMDD/<批次>/<原名>` | 分支、游离提交或历史保存 | 被保存的原提交；只留本地 |

发布标签都用 annotated tag，创建后不改、不删、不重打。错误标签保留并注明撤销原因，用下一个序号替代。历史轻量标签原样保留。归档引用不冒充发布标签。

main 标签说明必须包含：发布提交、实际全量验收提交、已知状态文件、四条线各自 collected/executed/passed/failed/error/skipped/timeout/not-run 数、差异与例外裁定、证据位置。采用第 5 节“留档提交”规则时，写明两个提交及逐字节对照证据。预览标签引用对应 main 标签与发版记录，补充换版原因、前一版本和部署记录，不谎称新做了一轮总闸。

产品版本同时修改 `pyproject.toml` 的 version；该修改先在普通任务分支交付，再验收、定版、打产品标签。1.0 前使用 `0.Y.Z`：不兼容变化或一批新能力增 Y，仅兼容修复/内部整理增 Z；是否发产品版本及升哪位由用户决定。
SDK 公共接口、持久格式（journal、回执、封存计划）或历史恢复能力的变化都要声明兼容性。平台源码身份可能随修改变化，必须核实旧任务恢复准入；不能仅凭版本号、dag_id 或“内部重构”声称旧运行可恢复。留存旧提交、环境依据及数据，禁止重写旧封存身份来绕过校验。

## 4. 合入闸：提交合并之前

管理者先核对 integration 干净、没有其他合并或针对它的验收正在读取可变源码；记录当前 HEAD 和任务交付 HEAD。合并期间只允许一个管理者写集成树。测试中的候选保持固定，或另用游离检出隔离。

在集成树试合并，闸通过且待提交内容与受测内容一致后才提交：

```bash
# 以下变量须设为实际路径/任务名，EVIDENCE 位于仓库之外。
git -C "$INTEGRATION" merge --no-ff --no-commit "$TASK_BRANCH" || exit 1
MERGE_TREE=$(git -C "$INTEGRATION" write-tree) || exit 1
if "$PYTHON" -B "$INTEGRATION/tests/merge_gate.py" --json "$EVIDENCE/merge-gate.json"; then
    git -C "$INTEGRATION" diff --cached --check || exit 1
    git -C "$INTEGRATION" diff --quiet || exit 1
    test "$MERGE_TREE" = "$(git -C "$INTEGRATION" write-tree)" || exit 1
    # 再核对回执、额外 untracked 文件及受测内容；通过后提交。
    git -C "$INTEGRATION" commit -m "Merge $TASK_BRANCH"
else
    git -C "$INTEGRATION" merge --abort
fi
```

上面是分步操作示例，不是无需判断的自动发布脚本。命令失败、冲突、dirty 或证据缺失就停下，不继续 commit。冲突由管理者明确归属，在任务分支修正或以隔离整合任务解决，不能覆盖他人工作。

合入闸必须确认导入本树、七个冻结文件、完整守卫集合和用例结果。缺失守卫、失败、异常退出、未解释跳过均不算通过；工具当前 `ok` 字段不能豁免额外检查。保存合入前 HEAD、任务 HEAD、受测 staged tree、合并提交及命令/环境/回执。

冻结文件或守卫集合的变更须有明确范围裁决、必要性、兼容性说明及替代/新增反例验证，同批审查源码和守卫修改。**禁止只更新 FROZEN 摘要、删除守卫或放宽断言来消除红灯。** 冻结范围外的普通合并不需要重复请求授权。

## 5. 总闸：main 前进之前

1. 固定验收提交 T，记录环境、依赖、完整文件/nodeid 清单、所有私有资源路径和运行命令。正在运行的 T 不再合入新内容。
2. 用 `tests/runtime_v3_regression_inventory.py` 生成 collection 与 execution 回执，运行 standard、ray、historical、historical_ray 四条线。清单、并发和超时预算随发版记录保存。仅收集不是运行；抽测不称完整总闸。
3. 用 `tests/engine_known_state.py compare` 与上次发布记录明确指向的清单逐条比对。比较工具发现任何差异都可能非零，包括修复后通过；逐条判断 new_non_pass、changed、now_passing、缺失/新增用例和未报告项，不能只看退出码或只比通过数。
4. 新失败必须修复；带新失败发布须用户对具体项明确同意，记录原因、影响、负责人和原消息依据。旧的已知失败不是通过，也不因复制到新清单自动获准保留。新增 timeout、error、skip、deselect、未执行/缺失回执与范围缩减同样必须解释，不能靠缩小清单获得“零新失败”。
5. 使用 `tests/engine_known_state.py build <spec.json> <out.json>` 生成绑定 T 的新清单，保留原回执与失败文本。另列本轮差异裁定及已经授权的范围例外，例如暂缓的性能测试；例外未执行计入 not-run，不计通过。
6. 影响工作台的改动由负责人提供固定提交的浏览器验收，覆盖本次真实用户路径。未改界面/交互的版本可以附理由记为不适用，不能虚构浏览器验证。

**偶发失败：** 同一提交、同一测试与已记录环境下至少三次独立复跑，保留全部成败、次序和并发条件；一次复跑成功不能覆盖首次失败。结果有成有败只能证明波动，不能证明没有产品缺陷。进入非阻塞已知不稳定名单还须有影响判断、负责人、处置和裁决依据；本次新发现且原因/影响不清的失败仍按新失败处理，不可由管理者自行贴 flaky 标签放行。已批准名单里的再次出现仍记录，不计成通过。

**验收提交与留档提交：** 清单记录自己所验收的 T；把该清单提交进 Git 会产生新提交 R，不能要求它自引用 R。允许通过隔离文档任务把清单/说明合入 R 后定版，条件是 T→R 仅有明确列出的文档/验收记录变化，运行源码、静态资源、依赖/打包/运行配置均逐字节相同，且最终合入闸通过。发布记录与标签同时写 T 和 R，不修改旧回执 head/input 摘要。

如 T 后另改测试，也须完整列出差异、定向执行实际修改的用例、证明原范围与失败反例未削弱，并按上段核对所有运行输入；未经核实不能沿用总闸。运行代码、依赖、资源或配置变了就对新候选重新执行总闸。证据的原始提交、增量验证与最终发布提交分别记录，不混成一次“全绿”。

## 6. 定版、推送与留档

定版前管理者核实：T 的总闸已收口、所有差异有裁定、最终合入闸通过、目标 R 是 integration 的确定提交、当前 main 是 R 的祖先。正式目录必须在 main 且干净，包含 untracked/ignored 冲突检查；检测依赖正式路径的进程、导入路径、可执行文件和服务配置。不能只检查进程 cwd。发现依赖须核实实际调用范围：只有继承路径未使用，或已证明服务当前及后续调用所依赖的文件逐字未变，才可记录不受影响；范围不清或确会改动在线消费者代码时，先由服务负责人迁移/排空，不能顺带换其脚下的代码。

若正式目录仍有未提交内容，先停在原状态：逐文件保存内容、模式、symlink、staged/unstaged 补丁和 SHA-256 清单并核验恢复。记录“提交入库 / 工作区档案保存 / 待负责人处理”的去向；不能仅移走后不留索引，更不能称这些内容已进 main。未经授权不把原文件覆盖回新代码。

完成上述条件后，在正式目录执行版本落位（这是部署动作，不是开发或测试）：

```bash
git -C "$FORMAL" merge --ff-only "$RELEASE_COMMIT"
git -C "$FORMAL" tag -a "$MAIN_TAG" "$RELEASE_COMMIT" -F "$EVIDENCE/tag-message.txt"
git -C "$FORMAL" push --atomic origin main "$MAIN_TAG"
git -C "$FORMAL" ls-remote origin refs/heads/main "refs/tags/$MAIN_TAG" "refs/tags/$MAIN_TAG^{}"
```

远端 annotated tag 的对象号不同于提交号；应核对 peeled `^{}` 指向 R，main 同样等于 R。不支持原子 push 时先记录原因、逐项推送并核对，部分成功不能记为全成功。网络失败只记本地已定版/远端待同步，不回卷 main。禁止 `--force`、`--mirror`、`--all`、整批 `--tags` 或推送归档引用。

代码与历史文档公开推送已有真人授权；沿用授权范围，无需每次重问。新增秘密、业务数据或超出既有公开范围的材料不因该授权自动公开。不要把私有服务 token、密钥或用户数据放入发布证据。

每次定版留下四项：

| 材料 | 位置/必需内容 |
|---|---|
| annotated main 标签 | §3 的身份、结果和例外 |
| 已知状态清单 | `docs/engine-known-state/<T短号>.json`，原始 T 与输入摘要 |
| 发布记录 | `_demiflow/shared-review/releases/<main标签>/`；包含 T/R/上一版、合入提交、两道闸、四线差异、例外依据、源码对照、推送核验、预览是否更新、清理与恢复位置 |
| 原始证据 | 回执、完整命令/环境、文件清单、日志、超时与失败、复跑、校验摘要；从 /tmp 汇总到持久目录，不复制业务数据或凭据 |

发布记录可使用 `REPORT.md` 加 `publication.json`，至少记录 `tested_commit`、`release_commit`、`main_tag`、`known_state`、`gate_receipts`、`lane_receipts`、`differences`、`exceptions`、`remote_verified`、`preview`、`archives`。最终提交号和远端状态写在仓库外，避免为改记录制造无限的新发布提交。

## 7. 预览换版

“已合入”“已发布 main”“预览已更新”分别报告。预览不随分支引用变化、静态资源变化或代码合并自动升级。新服务不得运行在任务树/集成树；已有服务依赖旧树时先登记保留，迁移前不能为满足目录规范强删或重启。

换版步骤由服务负责人完成：核实实际进程/端口/加载代码与静态资源 → 确认活动运行、Notebook、开发对话及用户未保存内容 → 按既有授权排空和备份 → 建立目标预览标签与固定树 → 用实际启动环境重启 → 核对端口、身份、接口和关键页面 → 留部署记录。
已有持续授权且排空条件满足则继续；会丢失用户未保存状态或终止未授权业务时，先处理具体风险。

记录 Python 加载版本、静态资源版本、PID、解释器、实际端口、部署前后标签和状态恢复结果，不能仅凭磁盘 HEAD 推断服务版本。预览失败可回到上一预览标签重启；保留原标签与失败记录，不重写历史运行身份、Notebook 或业务数据。

## 8. 热修、回退与独立复核

- 热修从当前 main 拉隔离分支；若修的是指定历史发布，说明基线及与当前 main 的兼容/合流方案。保持改动窄、保留失败反例，合入闸不可省。默认仍跑总闸；仅用户明确同意时可以先以受影响线定版，标签写明缺失项、负责人和一天内补验计划，不能宣称已补验。
- 未发布或已发布的问题合并，均通过隔离修复分支上的反向提交（对合并提交正确选择 `git revert -m 1`）回到 integration，重新过闸、定版。禁止回卷 main 或强推。
- 紧急服务止血在独立预览/部署检出切回旧标签；正式 main 目录保持 main 身份，不把正式目录临时切成 detached 后还声称“与 main 一致”。涉及持久格式变化须核实回退兼容性，不能用代码回退覆盖新数据。
- 每个产品版本须由另一方独立复核，日常 main 定版按用户要求安排；复核使用自己的检出与资源，不与管理者并发写树。记录复跑、清理恢复抽查和偏差。复核可在定版后进行，但不能替代定版前总闸，也不能提前声称已获独立通过。

## 9. 清理与归档

每日有维护工作时及发版收尾执行一次只读巡检，不新增自动定时任务：

```bash
"$PYTHON" -B "$INTEGRATION/tests/repository_sweep.py" \
  --repository "$FORMAL" --trunk main --integration integration \
  --json "$EVIDENCE/repository-sweep.json"
# 如需核独立克隆，逐个追加 --clone <路径>；旧挑拣历史另用 --patches。
```

每个保留项标明用途、负责人、提交、dirty、活动服务及下次清理条件。目标是去掉不用的树，不是追求固定数量；业务仓库的树不能按平台同名目录处理。

移除前查 tracked/untracked/ignored、staging、子仓库或挂载，以及 cwd、打开文件、已加载模块、命令行、PYTHONPATH、可执行路径和服务配置。未知占用保留并说明；不终止别人的进程来完成清理。

分支和游离 HEAD 先留下归档引用，再移除引用/树。dirty 与有价值的 ignored/untracked 全部保存，包括文件内容/权限/symlink、独立的 staged/unstaged 补丁、原提交及清单摘要；保存 index 所需的模式信息与可恢复说明。仅 `git diff`、stash 或只有提交号不足以保存未跟踪文件。归档验证通过才移除；每类归档首次做真实恢复验证，后续逐项摘要校验。历史 stash 先完整导出并验证可恢复，再按清理授权移除。

新归档统一 `refs/archive/YYYYMMDD/<批次>/…` 与 `_demiflow/archives/`，既有多名字空间保持可恢复，不为了统一外观重写。发布标签不删，归档的保留期由用户决定；没有明确授权不清空历史归档。记录清理前后数量、每项原名/路径/HEAD、档案位置与恢复命令。工作树移除不等于历史删除。
