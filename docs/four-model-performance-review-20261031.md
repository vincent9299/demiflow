# 四模型统一性能实现与验收（2026-10-31）

范围：pplx-decider-v1.2、amos-1-large、d3-turbo、AutoTrust-JEV-27B-v1.1 文本。
设计见 [统一性能方案](four-model-performance-design.md)，使用见
[模型服务](model-services.md#四个本地模型的统一性能入口)。
原始报告和临时探针保存在 `/tmp/demiflow-four-models`，不提交模型数据、运行环境或权重。

## 实现 review

- 保留 Dataset 算子负责行并发、重试、预算和 journal；services 负责生命周期与
  HTTP 准入。没有新增第二套业务调度器、HTTP 转发代理或后台捕获队列。
- `performance: optimized` 是统一声明。Torch 后端展开为有限 CUDA Graph 配置；
  JEV 展开为 `request_pipelining: true`，保持 vLLM 引擎的原容量、精度和插件。
  具体选项纳入部署身份，旧配置不自动切换；新配方仍须 prepare。
- 公共 `cuda_graphs.BoundedExecution` 不依赖某个模型结构，管理固定线程/stream、
  工作区准入、显存与缓存预算、捕获排他锁和关闭。后端申报工作区估算。
  `NativeGraphAdapter` 管理 tensor-tree 图；AMOS/d3 提供原生阶段薄适配。
  pplx 复用同一资源执行基类，保留已验证的原生 readout 图。
- 权重共享且校验地址一致，可变模型状态每 lane 隔离。AMOS 保留原生 FP32
  readout/校准；d3 保留 state-once、原生问题批次和排列平均。
- GPU 读租约覆盖 AMOS/d3 的完整原生调用；捕获前同步、释放读锁再升写锁，
  避免两个 reader 同时升级死锁。图输出复制到普通 allocator 后交回上层，
  避免下一阶段捕获/淘汰造成悬空引用。图使用独立池及 cuBLAS 工作区。
- d3 预算计入 recurrent matrix 和卷积切片保留的整个父存储；问题阶段仅把
  不可捕获的 CPU→GPU 索引创建提前，校验对象仍是未修改的原生 questions。
- 首次及周期校验逐 tensor 完全一致，失败返回原生结果、清空并停用图缓存，
  保留已经验证的独立原生 lane。未知 CUDA 异常使实例失败。
- 新增统一 `services benchmark` 单条/并发入口。报告 schema 与 batch 证据
  分离；通过此测试不能开启合批。真实冻结配置的 JSON 启动序列化已修正。
- JEV 保留 provider 的实际 usage；多问题累计，缺失不编造。batch 候选只有在
  provider 总量与原生 prompt token/单次输出严格相符时才按行归因。
- prepared identity 记录图执行源码、AMOS decoder、Transformers，以及可选
  Triton/FLA/causal-conv1d 等 kernel 包版本/缺失状态。

## GPU 质量与并行

只使用授权的 H100 80GB GPU 0/1。测试通过统一服务资源锁、独立临时部署启动；
没有重启已有服务，没有使用 GPU 2/3，没有修改安装环境或模型文件。

每模型测试集 200 条：100 条真实 identity 输入，100 条业务名称构造的 triage/
多问题输入，包含不同长度、noul、choice、不同选项数与顺序。不是人工标注准确率
评估。原生串行作为基线，逐次比较完整回答与 usage，概率容差为零。

pplx、AMOS、d3 均完成 200 条原生基线及 2,700 次原生并发/优化路径精确对照。
每模型另完成 1,000 个唯一 identity 请求、1,000 条请求/响应/usage journal，
停止模型后禁止重新 bind 服务并离线重放，输出完全一致且没有新增请求。

AMOS/d3 还分别完成：

- 原生 200 条与 1,200 次双流图/原生比较，全部精确一致；每实例 64 次捕获，
  分别发生 48/52 次淘汰，验证图生命周期。
- 另外 33 条较长文本/图片输入，逐形状捕获与重复调用共 363 次对照，全部一致。
  AMOS 32 条文本捕获、图片原生回退；d3 22 条捕获两个阶段，10 条因预算只捕获
  一个阶段，图片原生回退。不能把回退样本算作图覆盖。
- d3 额外 5,237-token 长输入在显式 72 GiB allocator 预算内通过 3 次精确对照；
  state 超图长度走原生，questions 捕获一张图，不能宣称整条长输入已图化。

三模型各自执行图输出故障注入：故意篡改 replay，校验返回原生答案并关闭图，
之后 6 条原生并行仍精确一致。超 token 请求在 GPU 分配前拒绝；64 MiB 小图
预算下不捕获、6 条原生结果一致。故障注入计数不是自然出现的质量差异。

最终 CUDA profiler 捕获两个独立 stream 的 kernel 时间区间交叠：pplx 9,212、
AMOS 9,172、d3 18,454 个 GPU kernel，均有跨 stream 重叠。这证明单卡独立
执行确实并行，不能用 HTTP 请求重叠或两张卡的副本替代这一证据。

JEV 的质量门槛与跨启动发现单独记录在下文；JEV `parallel=1`，CPU 准备/读出
流水线不是多个 GPU forward 并行。四模型生产跨请求 batch 均保持关闭。
最终 JEV 也完成 200 条新原生基线、2,700 次精确对照，以及 1,000 条唯一
identity 请求/响应/usage journal；66.79 秒完成请求，停止实例后 0.46 秒离线
重放，结果完全一致，没有重新启动模型或增加请求。

## 服务层性能

同样 200 条输入分布，原生单条与优化后的第三轮混合请求比较；后者并发为 2，
重复 3 次，共 600 条。计时不含模型启动和 journal。第三轮仍可能捕获新图，
脚本中的 `steady` 标签不代表全部命中或完全稳态。

| 模型 | 原生条/秒 | 优化混合条/秒 | 相对原生单条 | p95 原生→优化（ms） | 显存采样峰值原生→优化（MiB） |
|---|---:|---:|---:|---:|---:|
| pplx | 9.21 | 13.08 | 1.42× | 146→537 | 51,503→55,685 |
| AMOS | 9.62 | 12.15 | 1.26× | 141→567 | 54,551→58,735 |
| d3 | 5.44 | 7.52 | 1.38× | 215→357 | 62,087→58,599 |
| JEV | 12.13 | 13.47 | 1.11× | 201→309 | 65,545→65,543 |

这些结果提高吞吐，但不能宣称混合长度的 p95 也改善；排队与同步捕获增加尾延迟。
JEV 原有并发接口在整体请求锁下已达到 13.25 条/秒；新流水线相对此数只约 1.6%，
本次没有证明显著收益，不能把相对串行的 1.11× 全归于新机制。

另用相同 50 条高频输入比较优化模式单客户端与两个客户端，避免不同分布相除：

| 模型 | 优化单客户端条/秒 | 优化双客户端条/秒 | 双客户端 GPU 利用率均值 |
|---|---:|---:|---:|
| pplx | 25.04 | 30.59 | 94.3% |
| AMOS | 23.76 | 30.77 | 93.6% |
| d3 | 10.44 | 15.61 | 86.8% |
| JEV | 15.20 | 15.35 | 45.5% |

热输入表不能与上一表的原生混合输入相除宣称 3×。单卡利用率没有持续 100%。
JEV 热输入的流水线收益也小于 1%，不能描述为显著加速。
短任务的启动间隙、CPU 原生编码/读出、冷形状捕获、同步校验及后端原生内核仍是
性能边界。当前 AMOS/d3 环境没有 causal-conv1d，使用原生正确回退；安装或切换
融合 kernel 必须另做同样的输出对照，不能在此轮悄悄改环境换取更高数字。

## JEV 跨配置与跨启动复验

最初候选预设把 `max_num_seqs` 降为 1，跨配置对比在 case 51 失败：概率从
0.9808759631442909 变为 0.979667646768647。失败记录保留，没有放宽容差。
随后原容量 64 的两个新实例（GPU 0/1）完全一致，却也与旧基线不同：2 次标签
差异、163 个超零容差概率项、最大差 0.015619915723015632，usage 一致。
再在 GPU 0 单条串行跑容量 1，与这次容量 64 的 200 条结果完全一致。

最后另起原容量 64 的自有实例，捕获 200 条请求产生的 220 个原始 vLLM 响应：
旧、新适配器发出的请求 JSON 完全相同，重放同一份原始响应得到的答案和 usage
完全相同；再次直接调用同一后端的 200 条串行结果也完全一致。它与本次新原生
基线相同，与旧基线有 80 条请求的答案不同。这排除了本轮适配器请求转换与
概率读出的变更作为该差异起因，边界指向原生执行链路；尚未定位具体 kernel
或首次启动差异的全部触发条件，不能宣称已修复原生跨启动数值漂移。

因此该失败不能简单归因于容量变化或并发。最终预设保留原生引擎配置，adapter
只在后端请求期间持锁，保证至多一个 backend 请求在途，允许 CPU 准备和读出
重叠。不会为了高性能强迫 JEV 使用 pplx/AMOS/d3 的图执行器。

## 资源边界与未覆盖项

默认：两个固定 lane、全局 32 个图、图缓存 4 GiB、Torch allocator 64 GiB、
输入 8,192 token、单图 4,096 token、捕获 128 次/累计准入 60 秒；单次捕获可
超过剩余时间。热度表有限；低频或预算外形状回退，超单请求预算明确失败。

allocator 上限不涵盖驱动与所有第三方分配；NVML 数值为采样峰值，不是瞬时
峰值保证。CPU 编码字节/展开量有界，但不是 Python RSS 硬上限。图片与 pplx
多 chunk/超图长度仍有独占保护。当前三个图后端只支持单副本；原有多 GPU
独立副本部署保留。JEV 未验证单卡多个 forward 或跨请求 batch 无损。

有限样本与周期抽查不能证明所有未来内容/形状绝对数值不变。新模型、新精度、
融合 kernel、引擎版本或其他硬件必须重新对照；平台机制可复用，模型语义的
证明不能复用。当前优化不包含人工标注业务准确率验收。
