# JEV 单卡吞吐 review（2026-11-01）

## 结论与保留改动

保留一个公共缓存策略修正：热度从 shape 改为实际 `(lane, shape)` 图 key。
观察、准入、淘汰使用同一单位。四个模型后端共用它，不新增调度器、队列、
配置项或业务分支。模型输入、精度、计算、FIFO、CUDA stream、独占 gate、
缓存及工作区上限、质量检查均不变。

原策略把一个 lane 的请求量同时算在其他 lane 的同形状副本上，使很少使用的
副本也被保护。新策略保留真正频繁使用的副本，同一形状在两个 lane 上都频繁
出现时仍能独立并行。`min_observations` 现在针对每个图 key，因而某些图捕获
更晚；不能只报告预热后的最好成绩。

设计与事前 review 见 [设计](jev-throughput-design-20261101.md)。全部实验使用
本任务拥有的进程，未修改模型文件或已安装的第三方代码。

## 瓶颈证据

证据：`/tmp/demiflow-jev-bottleneck-20261101/diagnostic` 和 `comparison`。
前者测原始 200 条业务协议请求（含多问题、不同 readout 数量和长短文本）；
后者测 200 条业务 state 的真实 Dataset 身份判断链路，只有一个问题。
两组 prompt 不同，不横向比较绝对吞吐。

端到端旧策略每 200 条测量段的中位数：

- 输入准备合计约 **0.202 秒**。lane 准入排队很少，增加排队深度不能解决主要瓶颈。
- 原生 runner 合计约 **6.094 秒**；进入共享 gate 的累计等待约 **6.546 秒**。
  原生 runner 使用全局 forward/scheduler 状态，必须与图回放/捕获互斥。
- 约 4 GiB 缓存中有 28 张图，只覆盖 **16 种形状**。
- 每 200 条仍新捕获 **6 张图**，捕获合计约 **0.838 秒**；原生调用约 **91 次**
  （含捕获和周期校验）。这解释了仅优化 journal/线程交接为何没有明显提高 GPU 吞吐。

这些是不同线程的嵌套/并发阶段耗时，不能相加当作端到端时间。原生 runner
耗时包含 vLLM 调度、CPU kernel dispatch 和 GPU 工作，不宣称全部是 GPU 计算。
本轮证实可以改善的是公共缓存覆盖与捕获反复淘汰，并未改写 vLLM 内核。

## 对照与质量

一个 JEV 实例、GPU 1、两条 lane、同一模型/输入/原生基线、无合批。
先原生执行 200 条协议请求和 200 条 Dataset 请求。之后 ABBA 四块，每块排空并
释放旧缓存，再给相同的 1200 条预热和 600 条测量。旧缓存类直接从本轮修改前
快照装载，薄包装把新调用 key 转回旧 shape，保持旧策略原义。两种缓存从不
同时驻留。默认 4 GiB / 32 条目 / 128 次捕获 / 60 秒捕获预算保持一致。

每块的三个正式阶段顺序执行，各有 200 条、并发 2，走 Dataset → runtime →
journal → HTTP → 模型 → checkpoint。每阶段再校验 journal 重放、输出、请求
身份、usage 与 attempt 引用，跨阶段 SHA256 必须一致。轻量阶段定时在双方
一致开启，不开启 cProfile、py-spy 或 GPU tracing；无本任务其他 benchmark 同时运行。

对照总 **7600 次模型请求**严格一致，203 次图内部精确检查、0 mismatch。
额外初次诊断 2000 次请求同样逐条相等。这是已测试分布的证据；保留首次图
捕获及周期 hidden/score 严格校验，不放宽容差，不等同于任意输入的数学证明。

## 性能结果

下表是各策略 6 个正式测量段的中位数。

| 项目 | 旧策略 | 新策略 |
|---|---:|---:|
| 端到端吞吐，行/秒 | 18.67 | 21.30 |
| 请求 p95，毫秒 | 277.3 | 155.5 |
| worker CPU，秒/200 条 | 12.735 | 11.470 |
| 客户端 CPU，秒/200 条 | 0.896 | 0.993 |
| 原生调用/200 条（含校验） | 91 | 80 |
| 正式测量段新增捕获总数 | 36 | 3 |
| 缓存覆盖形状 | 16 | 19–20 |

测量段吞吐 **+14.1%**，p95 **−43.9%**。两个新策略块的吞吐中位数分别为
20.95、21.50，两个旧策略块约为 18.65、18.69，反向次序可复现方向。
不把同一缓存块内的重复测量当成大量独立实验，也不提供夸大的置信保证。

**包含全部预热时，整体吞吐仅从 17.73 到 18.51，提升约 4.4%**；单看预热
提升约 1.4%。新策略一次测量仍出现 3 次捕获并降低该阶段吞吐，尾延迟尚有波动。
这些阶段仍允许捕获，不是“捕获预算耗尽后的长期稳态”证明；未测得无限长任务
的固定加速比。冷门形状仍走原生互斥路径，不承诺 GPU 始终 100% 利用率。

两种策略合计观察到的峰值缓存为 **3,991,838,620 字节**（低于 4 GiB），Torch
allocator 峰值 **75,491,180,544 字节**（70.31 GiB，低于 74 GiB）。未扩大预算。
allocator 上限不包括驱动及所有第三方分配，不能宣称进程整体显存硬限。

## 回归与实现 review

相关 CPU 回归 **140 项通过**，包括四后端适配、质量失败停用、双 lane 同时
回放、FIFO、资源生命周期、部署/证据身份、SystemOne、journal 与重放。
新增行为用例验证冷副本不能借用热副本热度；热度表仍最多 `4 × max_entries`
条、计数饱和上限仍为 65535，没有新增每输入长期保留的状态。

JEV 对照结束后，在 GPU 0 上依次完成其他三个模型的回归。每个模型同实例原生
32 条 + 双 lane 288 条，包含长短输入、多问题及不同 readout 数量，输出严格
相等，图内部 mismatch 均为 0。为覆盖捕获/校验，测试配置使用
`min_observations=1`、`verify_every=3`、16 条目、4 GiB 缓存、64 GiB allocator，
捕获次数/时间预算为 512 / 300 秒；它们不用于性能比例推断。

| 模型 | 捕获次数 | 精确图检查次数 | 结果 |
|---|---:|---:|---|
| pplx | 47 | 70 | 通过 |
| AMOS | 51 | 75 | 通过 |
| d3 | 29 | 69 | 通过 |

不把 JEV 的加速比例外推到这些模型。未来 backend 可复用公共缓存和调度，
需要自行适配精确图 key、状态隔离和质量检查；纯外部 HTTP 引擎不会自动获得
平台进程内的 CUDA Graph。

## 证据与边界

`baseline/` 是任务开始时 129 个既有脏文件的副本及 SHA256；`comparison-source.json`
记录计时用生产和 benchmark 源码；`summary.json` 汇总结果。计时脚本后续仅补了
启动前磁盘预算检查，不改变被测算法或测量逻辑。业务代码及此前 journal 优化
未改；无 commit/push。最终 `preservation-audit.json` / `final-source.json` 记录
文件与源码审计，`resource-budget.json` 记录预算；全部自有进程已结束，GPU 0/1
无计算进程。未占用 GPU 2/3，未重启或修改既有服务。
