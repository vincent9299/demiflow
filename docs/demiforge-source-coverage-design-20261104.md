## 3. F-02：复用声明和静态依赖补足快照

### 3.1 内部覆盖依据

从现有登记导出一次操作内的源码依据；不写入新的项目配置。至少包括：

- 已有全部 `watch` 和公共 `sources`，不按目标 task 缩小；目标 pipeline 的自动 README/入口上下文也必须纳入。
- 适用 candidate.9 的明确入口文件、算子文件/目录、Notebook。项目范围内多个注册 pipeline 的显式作者角色均不能从 project-wide watch 中消失；跨 owner 的共享源仍保留其原所有者。
- 现有静态遍历能确定的本地模块、包初始化文件和 namespace 目录，以及缺失的必要目标。即使源码语法错误，已经有界读取的完整字节也应能作为失败依据被哈希；解析失败不能等同于“没有依赖”。
- 配置直接复用现有 `sources` 中的文件路径或明确的 watch 文件/子目录；不新增 `configurations` 清单，不从任意字符串或业务字段猜配置依赖。静态无法确定的动态文件读取仍是现有能力缺口。

建议把当前 `project_python_checks()` 的遍历抽成一个内部取证函数，返回所读文件摘要、必要路径/目录、保留语义的 import 边和诊断；`structural()` 继续复用它生成现有问题列表。快照和结构检查消费同一套路径依据，避免再实现一套 import 扫描器。可保留在现有 `checks.py` 内，`Project` 在方法内惰性导入以避免模块循环；无需新框架。

取证在一次操作内复用。不要在 `Project` 对象中保留跨 `current()` 或跨测试命令的长期缓存；verify 后必须读取新内容。为保持新项目可 start，缺失实现和语法诊断可随 draft 的取证返回，不能因此伪造通过；读取预算、路径安全或无法建立必要快照仍须显式失败。

### 3.2 精确穿透规则

快照仍复用原 `snapshot()` 的流式哈希、完整 Notebook 字节、目录/缺失标记和预算。新增能力只是在现代策略下携带必要的精确文件和明确作者子树：

| 场景 | 处理 |
| --- | --- |
| `operators: ["orders/runs/processing.py"]` | 只哈希该文件和必要目录状态；不递归读取 `orders/runs/history/`。 |
| 入口导入 `orders.datasets.transforms.clean` | 解析到实际源文件及路径上的 `__init__.py`，加入同一 watched 快照；未 watch/无合法 owner 时记录非通过，不能自动扩大 watch 或所有权。 |
| `sources.x.path = "orders/runs/settings.json"` | 在既有祖先 watch 下完整哈希该文件；上下文节选不减少哈希覆盖。 |
| `operators: ["orders/runs/transforms"]` | 这是明确的算子源子树，按原源码目录预算检查并哈希；不因此展开它的兄弟历史目录。该作者子树内的 `runs/datasets` 名称也不能继续产生隐含源码豁免。 |
| 精确 watch 根自身名为 `runs/datasets` | 该根是明确声明的输入范围，不因根名拒绝；按其实际声明范围取证，不能把它自动推广为所有同名目录的例外。 |
| 必要文件尚不存在 | 保留缺失标记，允许新项目 draft；check 非通过，创建/删除变化能被后续比较观察到。 |

遇到默认剪枝候选的祖先时，只沿通向明确必要路径的分支下探。精确文件例外不能变成祖先整目录例外；显式作者子树和仅用于到达文件的目录必须用不同状态表达。重叠 watch/角色/依赖对同一物理文件去重计量与哈希，不能给每个例外单独重置总预算。

### 3.3 信息不足时的取舍（需主会话确认）

**推荐采用保守边界：不能静默宣称宽泛 watch 的混合子树已完整覆盖。** 例如 `watch: ["orders"]` 下只有 `orders/runs/settings.json`，既没有精确来源声明，也没有受支持的静态依赖指到它：现有信息不足以把它判成配置，也不足以把整个 `runs` 判成产物。默认剪枝可以避免读历史，但必须显示该边界未核验；如果任务/验收需要这一范围的完整源码覆盖，则 check 保持非通过，不能把命名剪枝当作通过证据。原 F-02 的未单列来源配置样例应进入此用例，不能只修显式 operator 路径就声称全部问题已消失。

今后经授权可用**原有** `sources` 或更明确、可与产物分离的 watch/算子路径表达实际源文件；不新增另一份接入配置，不自动缩小现有 watch，不在本设计阶段更改真实 `project.json`。若既有声明把源码与真实历史产物混在同一个整目录作者根内，核心没有可靠的通用分类依据，不能同时承诺“完整遍历作者根”和“绝不读取其中未声明历史文件”。应先暴露冲突，由主会话确认原有声明边界；不能按文件名猜业务或靠增大预算强行读取。

这里的代价是部分模糊登记可能新增明确的未覆盖结果；收益是不以修路径名之名扫描历史，也不继续形成无依据的完整认证。暂不引入运行产物注册协议来消除这种歧义。

### 3.4 快照一致性与表示

- 保持 baseline 的现有路径到完整哈希/`None`/目录标记表示。必要目录和缺失目标必须有可比较的依据；不能只在 context 展示却不进入 fingerprint。
- 对取证时读取的源码摘要与最终快照逐项比对；包初始化、命名空间路径或文件身份在计划与哈希期间变化时拒绝该次观察并重试，不能发布混合依据。
- 当入口修改使必要依赖集合扩大时，在当前快照加入新路径，**不补写原 baseline**。从“以前未观察”转成“现在必要”不能自动断言历史文件没有变化；沿用 baseline 差异和写范围门禁，必要时保守阻断并说明覆盖扩大，不能 refresh 消掉。
- `context` / `handoff` 的 `excluded_directories` 不能继续将 `runs/datasets` 表述为无条件排除。添加有界的派生覆盖说明：所用标准/策略、默认剪枝候选、实际例外、未核验边界与截断/超限。它来自同一次取证，不是另一个由人维护的状态库；必要清单超限时失败，不能截断后标完整。
- readonly 继续复用独立快照与原显式只读根；不能借源码例外把 readonly 改成可写，也不从 import 自动授权读取外部环境。其精确来源若合法且已声明，不因 `runs/datasets` 名称丢失；宽泛只读树同样保留预算和诚实的剪枝覆盖说明。

## 4. F-01：保留 import 语义，局部修复缺失模块判定

保留 AST 的 `Import` / `ImportFrom` 类型、`module`、`level`、导入名称与别名、导入者路径/行号。不要继续把所有 `from base import name` 同等压成 `base` 和 `base.name` 两个必需模块。只收集有界静态事实，不增加可执行的 Python import 环境。

建议按以下顺序解析：

1. **先确定是否明确本地。** 相对 import 必须在本仓静态包路径内，级别逃逸立即非通过；已登记 owner/源码或实际本地模块给出了根据的绝对 import 继续走本地检查。未落在已绑定本地来源的外部绝对模块不扫描、不导入；记录未检查边界，保留原结构检查不证明第三方可用性/效果的限制。一个未声明的空同名目录本身不足以证明外部库被本地 namespace 取代。
2. **解析必需模块本身。** 逐段区分 `.py`、含 `__init__.py` 的包和有依据的本地 namespace 目录。已知为本地的必需模块找不到时必须返回诊断，不再返回“空列表即无问题”。缺失的中间包、文件作为包父级、符号链接、未 watch、无 owner、超限等也不能转成 external 放行。
3. **再处理 from 的名称。** 基模块是普通模块或包时，先识别其受支持的顶层函数、类、常量/赋值及 import 绑定。已知符号不要求同名子模块存在；再导出的提供方依赖仍进入同一遍历。对于包/namespace 中未定义的名称，只有确有相应子模块时才按子模块解析。必要符号/模块均找不到，或只能靠动态 `__getattr__` / 动态再导出猜测时，给缺失或不支持的非通过结果。
4. **继续执行原依赖方向规则。** 对真实模块身份及已经规范化的明确入口引用检查跨 entry 和 operator→entry；算子上下文沿 helper、包初始化、别名和再导出传递。不能因为采用 known-symbol 分支就跳过提供者或初始化文件。共享算子仍从既有 owner 导入，不重新登记所有权。

具体边界：

| import 形式 | 最小判定 |
| --- | --- |
| `from .missing import keep` | `.missing` 是必需本地模块；缺失即非通过，不去猜 `keep.py`。 |
| `from .processing import keep as k` | 必需模块存在且 `keep` 是受支持静态符号时正常处理，不要求 `processing/keep.py`。 |
| `from . import rules` | 先检查当前包已知绑定；否则需要本地子模块 `rules`；namespace 无初始化文件也可解析有依据的本地子模块。 |
| `from .helpers import keep`，helpers 的 init 再导出 keep | init 和实际提供者均参与哈希及方向检查；再导出链缺失、循环无法解析或超限时非通过。 |
| `from package import CONSTANT` | 静态已知常量不是模块；不假报缺失子模块。是否满足平台算子类型/效果契约仍归实际平台检查。 |
| `import external_pkg` / `from external_pkg import x` | 不为寻找本地文件而探测安装环境，不伪称已检查其源闭包；与明确本地缺失分开。 |
| `from .recipe import *` | 基模块存在性及反向依赖照常检查；不能靠 star 逃掉 entry 检查。未提供足够静态符号事实时，不以 star 证明后续名称已知。无需扩展成完整 Python 导出解释器。 |

本地模块/包同名、namespace 合并、扩展模块等来源不能确定时，显式不支持或不完整；不要用 `importlib.find_spec()` 等可能执行父包的机制猜。标准作用域仍是有界本地静态检查，不新增通用符号执行器或 purity 证明。
