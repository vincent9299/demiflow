# DemiForge 业务 Pipeline 开发定位

## 目标

**DemiForge 是提供统一开发标准的业务 pipeline 规范层。** 它不仅提供通用开发工具，
还明确规定 pipeline 应如何组织、实现和验收。开发者和编码 Agent 在同一套标准下，
结合项目业务需求和已有平台能力交付干净、规范、可维护、可验证的业务 pipeline。

通用不等于工程规范任意可配置。项目个性化用于表达不同业务，不用于让每个项目、Agent 或对话
另选一套工程结构。目标是提炼一套经实际项目验证、可持续改进的统一标准，而不是堆叠可自由切换的风格。

当前要解决的是实际开发经常跑偏：需求沟通不完整，Agent 未读取必要上下文，历史决定只存在于
聊天中，或已有规范没有进入实现与验收。优先改进这些问题，而不是先建设通用 Agent 调度平台。

“干净、规范”不是文件更少或抽象更多，而是读者能够从正式代码和配套说明看清输入、处理范围、
阶段关系、模型调用、输出与完成条件；职责和依赖明确，没有隐藏执行链和重复实现的平台能力。

## 开发对象与边界

开发对象包括授权范围内的业务 pipeline 入口、行处理算子、prompt、配置、测试、说明和 notebook。
既支持新建，也支持修改现有流程；不要求为了使用 DemiForge 而改装全部项目目录或迁移历史数据。

通用核心不绑定特定平台名称。本工作区采用 demiflow，业务开发时将其作为只读依赖。
DemiForge 可以检查公开契约、查阅平台文档，并通过公开接口
执行获准的验证；不能修改平台源码、内部协议、全局配置、共享依赖环境或服务生命周期实现。
这不是禁止正常调用平台 API，而是禁止把业务开发任务扩大为平台开发任务。

发现平台缺陷或能力不足时，记录业务需求、最小证据、受影响接口、已尝试的公开能力及阻塞范围，
交由单独的平台任务处理。平台维护者完成并验证后，业务任务再核对可用版本继续推进。
不得静默修补平台，也不得用业务侧客户端、调度器或私有接口绕过该缺口。

开发授权不等于运行授权。真实模型调用、外网采集、生产读写、全量运行、历史数据迁移与公共表发布，
按具体任务确认范围和资源预算；代码或模拟测试通过不自动扩大授权。

## 规范的归属

| 层次 | 权威内容 | DemiForge 的职责 |
| --- | --- | --- |
| 统一开发标准 | 目录与职责、正式入口、数据流编排原则、prompt 工程规范、上下文维护、测试与交付证据 | 提供统一基准、参考实现和检查，不交给各项目任意重定义 |
| 平台使用契约与适配 | 公开 API、数据流语义、模型及服务生命周期、资源与恢复契约 | 将统一要求映射到真实平台能力，引用实际版本，不重写平台或放宽标准 |
| 项目及业务定义 | 业务目标、实际处理阶段、表与字段、业务粒度、判定标准、具体 prompt 和阈值 | 在统一标准内表达项目差异，不硬编码进通用核心 |

Prompt 也按此分层：任务、输入、判断依据、输出契约、必要例子和实际请求检查属于可复用的
开发要求；如何判定某张图是正例、某道题是否有效、采用哪种评分标准，仍由具体业务维护。
格式或 schema 检查不能替代语义审查与效果验证。

主线显式编排、普通模型节点与局部 Agent 的职责边界、跨流程交接原则等属于要统一的工程规范，
不能由项目或 Agent 临时另选风格。当前 Dataset、模型算子及持久队列约定是首版标准的提炼来源；
具体平台 API 归适配层，业务阶段和判断条件归项目。平台差异只通过标准明确支持的适配表达，
不建立第二种业务编排语言，也不以项目配置关闭必需规则。首版标准发布前仍按既有现行规范执行。

每条规范只维护一个权威来源。DemiForge 当前唯一实现、标准与 Skill 在
`demiflow.forge.development` 包资源；公开入口是 `demiflow forge dev`，项目薄 launcher
保留 stdlib 用法。DemiOrch/Candidate 不随开发工具迁移。通用规则迁入时，应同步消费方引用和相关检查，
而不是在项目规范、AGENTS.md、skill 和 README 中复制多个可独立修改的版本。
迁移之前，原有现行规范继续有效；计划迁移不表示迁移已经完成。

## 统一与个性化的边界

| 统一标准规定 | 项目可以定义 |
| --- | --- |
| 目录职责、入口形态、依赖方向和配置归属 | 业务名称、具体算子、配置值和材料位置 |
| 数据流必须显式，模型与服务调用不隐藏在自管流程内 | 处理哪些业务阶段、合法分支及业务变换 |
| Prompt 必须解释任务、输入、判断依据和输出，按内容清晰组织 | 实际任务正文、业务例子、领域判据和输出字段 |
| 输入身份、处理范围、失败、复用、提交与完成状态的工程契约 | 表 schema、主键、业务筛选、模型选择和资源预算 |
| 必需检查、证据绑定、语义审查和交付状态 | 业务测试用例、质量目标和授权的试跑样本 |

统一的是职责与工程契约，不是把所有业务 prompt 强塞进相同标题，或让所有 pipeline 使用相同阶段。
合理差异需要标准明确支持；遇到不适用的规则，应提交标准修订证据，不能在当前任务中静默豁免。

## 防止不同 Agent 和对话造成规范漂移

以下是后续必须实现和验证的机制，不表示当前工具已经具备：

1. **项目绑定明确的标准版本。** 每次任务记录采用的标准及来源；规范变化不自动修改历史验收结论。
2. **统一参考实现和模板。** 从与标准一致的骨架开始，已有项目按明确范围迁移；旧代码不是豁免依据。
3. **续接仍使用同一约束。** 重新读取当前需求、有效业务决定、源码和任务证据，不靠聊天记忆重新猜规范。
4. **检查不能由 Agent 自行省略。** 可机械判断的规则进入检查器，行为规则进入测试，语义要求进入审查；
   必需项失败、缺失或尚未验证时，不得标为通过 DemiForge 验收。
5. **结果绑定实际版本。** 源码、prompt、配置或适用规则变化后，重新确定受影响的验证，不沿用不匹配的回执。
6. **标准修订独立进行。** Agent 可以提出问题和改进证据，但不能为让本次实现通过而自行改弱规范、检查或验收条件。

标准应通过真实开发中的反例和跨任务回归持续改进，而不是在每个对话中重新定义“最佳实践”。
声明通过验收时须说明适用标准、检查范围和剩余风险，不能将结构合规等同于所有业务逻辑必然正确。

## 上下文如何进入开发

### 开始前

按以下来源确认任务，不依赖 Agent 恰好记得上一次聊天：

1. 当前用户明确的目标、修改范围、不可改变项和运行授权。
2. 消费方项目的 AGENTS.md、绑定的统一标准版本、业务补充定义及适用的平台契约；
   尚未迁移的项目继续明确引用其现行规范，不冒称已经通过新标准验收。
3. 目标 pipeline 的 README、实际入口、相关算子、prompt、配置和测试。
4. 与本次修改有关的已确认决定、固定输入输出引用及验证证据。

引用必须可定位，并在执行前核对当前内容。历史记录用于解释决定，不能覆盖已经替代它的现行规则。
代码证明当前实际行为，不自动证明它符合规范；旧测试通过也不能豁免现行要求。
与本任务无关的聊天和运行日志无需全部装入上下文，但不能为省略上下文而跳过必读规范。

涉及目标、数据语义、修改范围或权限的关键缺失必须指出并确认；允许自行决定的小型实现细节
应说明依据。冲突不能靠混合新旧规则或选择最容易通过的一条来解决。

### 开发中与续接时

需要留下的有效任务上下文包括：目标与非目标、采用的规范来源、可改范围、输入输出契约、
已确认决定及理由、验证证据、未验证项、待确认问题和下一步。
复用项目已有的任务或验收记录，不强制每次增加一套文件、配置协议或日志系统。

长期有效的业务决定回到目标 README；统一标准的问题进入其权威规范或现有 TODO；
一次运行的参数、状态和结果保留在已有运行记录中。新决定明确替代哪些旧决定，不无限追加相互矛盾的条款。
只有用户确认或可信验证支持的内容才能作为确定事实；建议和假设要保留其状态。

续接时先核对当前文件、差异和证据，再继续未完成工作。保留用户修改和已有历史产物，
不因上下文遗失而重新运行生产任务或重写已经提交的数据。

这套方式依靠可核对的项目记录减少对聊天记忆的依赖，不宣称 Agent 已具备自动、完整的长期记忆。

## 实现与验收

以项目绑定的统一标准和业务定义为准，使实际实现能够明确展示：

- 正式入口和职责归属；不会为调试、比较或恢复另建隐藏流程。
- 输入版本、本轮范围、行粒度、关联关系和输出字段归属。
- 业务变换与平台执行机制的边界，及已有公开能力的复用。
- Prompt 与模型的实际输入输出，必要上下文和判断条件。
- 失败、空结果、复用、恢复、资源限制和完成判定的真实行为。
- 改动对应的测试、审查、获准实跑及未验证范围。

验证强度随风险调整。结构检查、行为测试、语义审查、小样本实跑和业务质量分别报告，
不能用其中一项代替其余证据，也不为机械搬运无差别追加没有增量价值的全库扫描。
验收结果绑定实际被检查的源码、prompt 和配置版本；相关内容变化后重新判断受影响的验证。

规范文本负责指导；程序检查可以拒绝接受不合格交付；运行环境的权限和隔离负责限制真实副作用。
三者不能混称。DemiForge 没有覆盖的执行路径、资源上限和权限边界必须如实披露，
不能仅凭文档或 Agent 承诺宣称硬限制已经生效。

按实际所属路径登记，不再要求仓库根目录集中布局。唯一权威为该版 DF-02，
登记器检查所有权、路径安全和监测范围，结构检查解析静态导入关系及本地 helper 链。

全量操作须有明确用途，性能验证检查首条有效输出、吞吐及临时 I/O。该要求不等于自动性能证明。

明确绑定该历史版本的入口，不作为新建项目规则。旧入口按明确旧版本逐步迁移，
旧任务不能获得新标准的通过状态。全文件完整哈希与有界 Notebook 内容投影分离，
既有输出不因内存控制被排除出保护范围。具体格式与上限见 quickstart。

修正规则后连同参考实现和迁移说明发布；不宣称未经验证的规则已经是所有场景的最佳规范。
迁移时同步消费方引用、行为检查和验证；之后以版本修订持续改进，而不是让各项目自行维护规范分支。
