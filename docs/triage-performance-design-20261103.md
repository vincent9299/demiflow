# 真实 triage 性能：设计与事前 review

## 目标与约束

在 gpu32520 的真实 triage 输入上定位并改善单卡吞吐/尾延迟，沉淀可复用的平台
能力。业务 prompt、权重、精度、校准和跨请求 batch 不变。用户后续明确允许
先暂停真实跑批、修复后恢复；连续采样和记录进度后，按 PID 身份停止两个
生产者及所属服务，在空闲 GPU 上启动自有对照。共享环境只读，不
commit/push，保留所有既有工作树修改。私钥配置只用于 SSH，不修改、不复制。

## 核查顺序

1. 只读读取运行实例身份、版本、kernel 包、GPU、图命中/校验/捕获/淘汰和排队
   计数。用同一段时间的增量计算，不能把校验时的 native + hit 双计为两个请求。
2. 从生产 journal 只读抽取最多 200 条已完成的原始请求/响应。保留 state 的字符串
   类型、criteria 顺序、问题和 usage，不从名称重新拼造测试 prompt，不扫描全表。
3. 空闲后对同一批请求分开测模型、HTTP 和 Dataset+journal。重型 profiling 与
   正式计时分开；记录编码、排队、模型 forward、readout、图回放、同步/复制及
   端到端延迟，解释计时边界与并发重叠。
4. 分别改变 CUDA streams（1/2/3/4）与客户端在途数（至少 2/4/8），固定其他预算。
   `streams=2` 是当前默认，不是要求；不把更多排队冒充更多 forward。
5. 在隔离环境验证 causal-conv1d。先确认实际 dispatch 路径及 ABI，再做同输入
   完整回答、usage、概率逐项精确对照。kernel 的数学等价不代表浮点逐位等价；
   若融合激活改变舍入，不放宽门槛，继续定位或不启用。

## 架构与候选 review

公共层负责部署/执行身份、资源预算、lane 准入、指标及验证；后端保留模型输入与
计算协议。不会给 triage 加专用业务分支，不为多客户端加第二套调度器。
先按 profiler 的实际耗时选择优化，不默认提升 streams 或安装 kernel 就会变快。
部署缺少加速依赖可以如实呈现为能力状态；`optimized` 不应被理解为所有内核均最优。

GPU 100% 只表示忙碌，不能证明 CUDA Graph 命中或理论极限。Little's law 要使用
同一边界内平均在途与平均耗时，不能用并发上限/p50 推出性能上限。之前“两个
客户端”基准实际是同一 HTTP client 内两个并发 worker，不构成拆成两个业务进程
必然加速的证据。固定文本前缀也不能未经模型语义验证就复用 state/prefix cache。

## 资源和验收

- 在线只读查询最多每 30 秒一次；单次响应最多 1 MiB；SQLite 点查短事务、超时
  1 秒，每条请求/响应合计最多 32 KiB，样本最多 200 条/8 MiB。不写生产数据库。
- 独立环境/下载/编译预留上限 32 GiB，诊断/trace/journal 上限 2 GiB；分阶段检查
  实际占用，达到上限停止新增。CPU 编译最多 2 jobs，GPU 不参与编译阶段。
- GPU 对照一次一个模型进程，单卡，只在 nvidia-smi 与资源锁确认空闲后启动。
  延续 64 GiB allocator、4 GiB 图缓存和输入预算；lane 数增加时共享总预算，
  不能无限增加显存。每个子进程有超时、退出/取消时清理自有进程组与服务。
- 先小样本筛选，再 200 条、交替顺序的端到端复验；记录预热和捕获预算耗尽后
  的稳定结果，避免只优化一组热形状。稳定收益与偶发改善分开报告。
- 新 kernel、streams 或执行方式均需质量对照。保留原生基线、标签/概率/usage
  精确比较及现有图内部校验；未知 CUDA 错误失败关闭，不伪装成安全回退。
- 设计和实现各做 review；仅保留有真实收益且质量通过的候选，补充通用契约、
  资源边界和针对性 CPU/GPU 回归。不承诺未经测量的固定加速比或任意负载最优。

## 本轮实测后的设计 review

- 原运行版本正确，真实窗口图回放命中超过 99.9%，未发生捕获/淘汰风暴。65 秒
  GPU 采样平均 98.1%/97.7%，短时最低 74%/71%。需要同时处理低谷与每请求 GPU
  工作量；不能把 GPU busy 指标当作吞吐结论。
- 官方 causal-conv1d 融合 SiLU 改变 BF16 舍入位置：pplx 200 条中 147 条概率
  改变、1 条标签改变，AMOS 116 条改变、2 条标签改变。因此拒绝直接安装后
  自动启用。先卷积落回 BF16、再调用原 SiLU 的候选，两模型各 200 条均完全一致。
- 同实例 pplx 对照：原图 20.52、分开舍入的卷积 22.88、只融合归一化逐元素运算
  21.23、组合 23.59 条/秒；最后重测原图 20.68。此为短阶段适配器实验，含少量
  尚未热起来的形状，不代替生产稳态、HTTP、Dataset/journal 或持续利用率验收。
- 周期校验保持每 64 次、完整精确比较。已有图的 native/replay 校验只读共享权重，
  无需阻塞其他 lane；改为保持当前 reader lease。发现差异立即禁止新图回放，再
  获取 exclusive lease 排空其他读者后释放图池、返回该行原生结果。捕获/淘汰/
  关闭仍必须独占。CPU 测试须覆盖两 lane 真正同时校验，以及失败后的排空和释放。
- 新内核仅允许作为图捕获候选：原生参考计算必须保持不变，不能把优化后的模型
  同时充作质量基线。任何正式集成必须保留捕获时与周期性的原生比较；图池、显存、
  捕获次数和时间预算不增加。归一化仍使用原 float32 square/mean 和 gated SiLU，
  不改变归约顺序；所有 BF16 中间舍入显式保留。实验代码尚不构成部署批准。
- 继续验证只依赖现有 Triton 的卷积实现，避免为一个小算子引入 CUDA 编译工具链
  或改变 Transformers 的原生依赖探测。若不能逐项一致或无收益则不集成。

## 端到端 CPU 热点与最终边界

200 行 Dataset 对照中，GPU forward 之外仍有约 8–11 秒启动空档。定位到公共
artifact resolver：初始化 journal 时，每个新进程完整解析工作区 784,536,748 字节
的 `artifact_locations.json`。不是 SQLite 写锁，也不是业务请求太少。

超过 8 MiB 的重定位 manifest 改为流式生成可丢弃的 SQLite 点查索引；JSON 仍为
唯一来源，按完整源路径精确匹配，alias 优先级、重复键最后一个生效、原请求身份
和 journal 内容不变。缓存身份包含设备、inode、size、mtime、ctime；生成前后核对
源身份，完整写入并 fsync 后原子发布。小 manifest 保留原路径，不引入第二套
journal、业务过滤或额外依赖。

资源上限：源 1 GiB、500 万条、单个 JSON token 16,384 字符，128 条写入批次，
SQLite 页缓存 8 MiB、单索引 2 GiB、缓存目录 4 GiB/16 个索引。目录最多检查
128 项，只回收本模块命名的衍生文件，保留其他文件。锁等待最多 120 秒，构建逐条
检查 110 秒预算；超限明确失败。只读连接用完关闭；点查 LRU 最多 1,024 项。
这些约束不等于整个 Python 进程的 RSS 硬上限。

真实 manifest 一次索引构建 14.08 秒、索引 845 MiB；同一远端机器的只读 200 行
重放，旧实现 13.08 秒，新实现 0.579 秒。独立按原 JSON 物理行解析的 229 个分散
记录全部匹配，源文件身份不变。

最终图捕获只优化已识别的 Qwen3.5 模块，保持原生函数作为独立参考。卷积使用
无 bias 的 BF16 路径；带 bias 的跨布局测试发现差异，因此回退原生。不同长度
不是白名单，JIT 不按长度/stride 特化。归一化保持原归约与舍入。临时替换只发生
在独占捕获作用域，异常也恢复；外部已安装卷积内核不覆盖。新源码纳入部署身份。
