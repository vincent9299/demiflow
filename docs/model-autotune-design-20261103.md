# 模型部署自动调优：设计与事前 review

目标：复用现有部署、HTTP worker、BoundedExecution 和质量对照；在明确资源预算
与质量条件内选择实测最好的执行配置。不是任意未知模型的自动代码生成，也不保证
全局数学最优或所有输入 GPU 始终 100%。不增加业务调度器、不修改业务 prompt。

## 身份与入口

新增显式 `services tune --config ... --cases ...` 部署阶段命令，`prepare` 仍然
不加载模型。`performance: auto` 复用四个已支持 profile 的优化设置作为稳定声明；
与对应 optimized 声明保持相同逻辑模型身份。最终 streams、CPU 线程、在途数及
图缓存策略保存为独立执行档案，不改声明、不重写 journal。原 native/optimized
路径不自动应用新档案，不改变旧配置哈希。

auto 执行要求存在有效档案；缺失、损坏、过期或环境/硬件改变则明确拒绝并提示
重新 tune，不能在第一行业务请求时偷偷跑基准。当前原生 vLLM profile 没有统一
任务质量比较器，不伪装成支持自动质量验收。后续 backend 通过同一能力配方声明
接入，协议、状态隔离和原生参考仍由 backend 负责。

## 搜索与质量

- 先运行独立原生参考，之后候选完整响应与参考精确比较；参考路径禁用图和候选
  内核，JEV 使用已修复的原生 runtime，避免切换为另一个 vLLM 启动配方。
- 至少 400 个不同请求，确定性划分搜索集与留出集，各至少 200；不能重复 200
  个输入充当留出集。搜索/预热不使用留出集，最终候选另起进程复验留出集。
- 候选限于配方允许的执行参数：独立 streams、在途上限、CPU 线程、图缓存容量
  和捕获热度。输入上限、精度、权重、校准、问题/答案、校验频率和 batch 策略
  不参与搜索，不降低质量门槛。跨请求 batch 继续关闭。
- 每个候选用有界 HTTP 客户端持续供给，完整比较输出，分别记录冷阶段、预热后
  多轮吞吐、p50/p95、图命中/校验/失败和显存。原生基线与候选服务分别拥有生命周期。
  首版调优指标边界是客户端 HTTP 编码到完整响应，不包含任意业务前后处理；本次
  最终选中配置另用真实 Dataset/journal 做端到端回归，不能把 HTTP 当整条业务链路。
- 按吞吐或延迟目标选择满足约束的候选；收益接近时倾向较少在途、较低资源成本。
  有限候选和时间内没有合格结果则不发布；错误和 CUDA 异常清理本次服务后记录。
- 后端配方的准入先于实测排序：已复现非法显存访问的 AMOS 3/4-stream 不进入候选，
  也不能通过伪装为成功档案绕过。AMOS 保留 1/2-stream，其他三种后端保留 1–4。
  有限样本偶尔通过不能消除已知并发缺陷；更宽执行需在修复后重新开放和验证。

## 预算和发布

配置与结果最多 1 MiB；请求文件最多 16 MiB、每行 64 KiB、最多 2,000 条。
响应每条 256 KiB、每阶段总计最多 32 MiB；只保存有限摘要和输出摘要哈希。
默认最多 13 个候选，最多 1,800 秒；最大搜索时间和候选数在解析时检查。请求
超时、连接数、活跃 worker、预热次数和测量轮数均有上限。日志每服务 8 MiB，
调优工作区最多 512 MiB；临时 HTTP 服务复用资源锁，拒绝占用的 GPU，不接管
现有服务。显存和图缓存不得超过原声明；实际设备还要保留余量。

档案绑定原模型契约、权重签名、adapter 源码、runtime、执行环境、GPU/driver、
CPU 可用核、样本摘要及质量策略。完整验证后原子发布到部署目录，活动进程不会热切换。
复用仍做身份校验；这不是每次业务执行重新跑基准。未知输入形状仍受原图门槛、
原生精确校验与资源预算保护，有限样本不能宣称覆盖所有未来输入。

## pplx 改进候选与 review

先缩小新图捕获前原生参考的独占范围：在当前 lane 的共享 reader 内完成原生参考，
捕获/释放才进入独占；NativeGraph 同理。保留输入/输出生命周期和两 lane 同时
申请独占时的排空语义，CPU 测试覆盖并发与质量失败。JEV 原生 runtime 有全局
状态，保持独占，不套用此改动。

结果回传的 pinned-memory/event 流水仅在时间线证明有收益、严格质量和生命周期
检查通过后采用；不直接删除同步。性能前后对照绑定本轮源码快照，CPU 回归先行。
开始实现时 GPU 0/1 被其他任务使用；确认空闲后才运行本次隔离实验。
不改共享环境，不 commit/push。

## GPU 实验发现的 Triton 提交状态竞争

AMOS 的并发冷路径在旧实现和本轮实现均出现故障。独立诊断捕获到 Triton 3.8
`Autotuner.run` 的 `self.nargs` 被另一调用清空，导致调参 hook 读取到 `None`。
这属于共享 CPU 提交状态，不能用整个 forward 串行化掩盖。

在拥有生命周期的多 stream worker 启动时，对包含该共享字段的实现安装一次
实例级 RLock：只保护单个内核的调参、参数和提交，异步 GPU 工作提交返回即释放。
不同内核可以同时提交，图重放不经过此锁。每个内核对象最多一个锁，没有随请求
增长的全局登记表；只改本进程方法，不写模型环境。原生串行参考不安装此保护。
Triton/FLA 相关源码进入准备身份，CUDA/Triton/FLA 环境变量进入调优身份。
质量门槛仍以独立原生对照为准，不能把不再崩溃当作质量或全部根因已验证。
